# Design Decisions & Progress Log

This document records the core architectural decisions, design guidelines, and changelog updates for the **Token Spark** project.

---

## Core Priorities (read before making any architecture trade-off)

Established explicitly by the user (September 2026), after a real incident
below showed what happens without this written down. In priority order:

1. **Two-way sync between Figma and GitHub that never breaks.** This is the
   whole point of the plugin. Nothing else matters if this is unreliable.
2. **Both Variables and Typography sync correctly** — not just Variables.
   Typography is explicitly part of "the core," not a bonus feature.
3. **The JSON committed to GitHub must be clean and genuinely usable by a
   team** — readable, sensibly split (e.g. a `primitives/` folder with
   separate `color.json`/size file/dimensions file, not one compounded blob),
   not merely "technically round-trips."
4. **References resolve correctly** wherever they're consumed — pulling into
   Figma, generating CSS/Dart/Swift/JS output, anything else built later.
5. **Theming works out of the gate.**

**`primitives → themes → semantic` layering is a real structural convention
— a "golden rule" — but it is explicitly *not* the most important thing on
this list.** It's in service of the priorities above, not an end in itself.

**Multi-collection-per-role support, the Size axis, Map Collections, and
collection provenance tracking are NOT the core.** They exist to make the
core above more understandable, flexible, and robust. They must never be
allowed to compromise it — if a flexibility feature's edge case requires
risky surgery on stable, well-tested core code, that is a signal to pause and
weigh the trade-off explicitly, not to keep patching narrower and narrower
symptoms.

**The incident that prompted writing this down**: chasing a real bug (Size
axis on Primitives combined with a multi-collection Primitives role) through
five narrow patches in a row, in increasingly deep parts of the sync/apply
logic, before stepping back to ask whether the underlying representation was
wrong in the first place (it was — `figmaToCollections` was compounding
shared primitives into every size mode's entry instead of exposing clean,
separate, single-role entries — see §1 "`figmaToCollections` Composite-Entry
Fix" once that lands). The lesson: when a "flexibility" bug needs more than
one or two attempts to actually fix, stop and ask whether it's really a core
issue in disguise (as this one turned out to be — clean, separate primitive
files *is* the core "usable JSON" requirement) before continuing to patch
symptoms in isolation. Also surfaced a real gap in priority 2: Typography
sync has never actually been verified end-to-end in a real Figma file,
despite being explicitly part of the core — worth prioritizing over further
edge-case flexibility work.

## 1. Core Architectural Decisions

### Native Figma Collection Mapping (Why not Token Studio?)
* **Decision**: We map Figma variable collections directly to W3C Design Token Community Group (DTCG) standard JSON structures.
* **Rationale**: Token Studio relies on proprietary internal token sets and requires the plugin layer to resolve aliases. Token Spark eliminates the plugin dependency for runtime compilation by mapping collections directly to standard file scopes, empowering developers to compile tokens natively.

### Dynamic Metadata-driven Collections
* **Decision**: Avoid hardcoding collection names (like "Primitives", "Semantic"). Instead, collection names are dynamically read from `metadata.json` under `figma.collections`.
* **Rationale**: Enables users to start from scratch with their own named collections without breaking the synchronization engine.

### Wiping Legacy N×M Modes
* **Decision**: Removed legacy `Legacy N×M brand×theme modes` rendering selector blocks and nested directories in `semantic/`.
* **Rationale**: Standardizes compilations to a flat theme structure (`semantic/{theme}.json`), simplifying file structures and preventing bloated CSS/JS selector outputs.

### Selective Syncing / Ignored Collections
* **Decision**: Added `ignoredCollections?: string[]` configuration in `metadata.json`. Entries are **layer keys** (`"primitives"`, `"global"`, `"themes"`, `"semantic"`), not Figma collection display names — they are matched against `figma.collections` at runtime.
* **Rationale**: Allows teams to mark certain collections (e.g., read-only core primitives) to be ignored during Pull/Push sync diff actions. Crucially, the platform compilers (CSS, JS, Dart, Swift) still receive the complete collection dataset to successfully resolve references.
* **Scope**: Applies to the pull diff, the push diff, **and Clean Apply** — an ignored collection is never written to or deleted from, in either direction. Only platform output includes it.

### Separate `js` and `ts` Platforms, One Generator
* **Decision**: `metadata.json` has distinct `platforms.js` and `platforms.ts` entries. Both are compiled by the same generator (`transformer/js.ts`), gated by a `typescript: boolean` option. TypeScript-only syntax (`as const`, `export type`) is emitted **only** when `typescript: true`.
* **Rationale**: A `.js` file containing `as const` is a syntax error at runtime (this shipped once — see PR #3's `dist/{colorScheme}.js`). Sharing the generator keeps the two outputs structurally identical.

### Combined vs Split Output Modes
* **Decision**: JS, TS, Dart, and Swift support two output modes, selected by the output path template. `{colorScheme}` in the path → **split mode**: one file per color scheme (semantic + global merged into `tokens`, primitives separate), resolved through the **default (first) theme only**. No placeholder → **combined mode**: a single file with primitives, global, per-theme constants (`themes` export in JS/TS, `DesignTokensTheme{Name}` classes/structs in Dart/Swift), and per-scheme constants. All platforms share one `compileSplit` helper in `transformer/index.ts`.
* **Rationale**: Split mode serves the common "import light/dark constants" case; combined mode is the only way to do runtime multi-theme on platforms without CSS custom properties. Theme classes are prefixed `Theme` so a theme named "Light" can never collide with the color-scheme class of the same name.

### Description Sync Is Export-Only
* **Decision**: Figma variable descriptions are exported to W3C `$description` on push. They are **not** compared in diffs and **not** applied back to Figma on pull.
* **Rationale**: Descriptions ride along whenever a value changes (push writes complete files). Making them diffable/applyable needs a UI decision about how description changes are reviewed — deferred (see Planned below).

### `fontWeight` Canonical Value Is Figma's Named Style; Translation Happens Per-Platform
* **Decision**: A `fontWeight` token's `$value` is always the literal font style name as Figma/the font names it (`"SemiBold"`, `"Regular"`) — never a number. On the Figma side, `fontWeight` maps to a `STRING` variable, not `FLOAT` (confirmed against real usage: Figma font weight variables hold the installed style name verbatim; numeric OpenType weights are a web/CSS-side concept, not how Figma or most fonts express it). Each platform transformer that needs a real numeric/enum weight (CSS, Dart, Swift — not JS/TS, which just passes the string through as data) converts it locally via a shared resolver (`shared/font-weight.ts`) built on DTCG's own `fontWeight` alias table (`thin`/`hairline` → 100 … `extra-black`/`ultra-black` → 950), matched case/punctuation-insensitively so `"SemiBold"`, `"Semi Bold"`, and `"semi-bold"` all resolve the same way. A style name with no numeric equivalent (`"Text"`, a custom font-specific name) falls back to 400/`.regular`/`FontWeight.w400` with a non-fatal `console.warn`, never a crash or invalid output.
* **Rationale**: Figma requires the *exact* installed font style name to apply a variable or bind a Text Style field — rewriting the canonical value into DTCG's exact kebab-case spelling would silently break Figma round-tripping for any font whose style names don't match DTCG's vocabulary (most of them). Keeping translation per-platform (rather than storing a second numeric field on the token) avoids a second source of truth and matches how every other platform-specific concern already works in this codebase (hex reordering, dimension parsing, etc. are all local to their transformer). This also fixed a real bug: no transformer previously special-cased `fontWeight` at all, so a value like `"SemiBold"` was emitted verbatim into CSS (`font-weight: SemiBold`), which is invalid — `font-weight` only accepts `normal`/`bold` or a number.
* **Also fixed**: `figmaTypeFromTokenType` never returned `"FLOAT"` for *any* token type — `dimension` and `number` (spacing, radius, font size, line height…) were mapping to `STRING` too, so applying those tokens created inert Figma variables holding literal text instead of real numbers, unusable for auto-layout gap, corner radius, stroke weight, or Typography Variable bindings. Now `dimension`/`number` → `FLOAT` correctly; `fontWeight` stays `STRING` (see above, this was verified rather than assumed).

### Typography Style Groups: Opt-In Group-Level `$type: "typography"` Marker, Fields Stay Decomposed
* **Decision**: This repo already decomposes composite typography into sibling leaf tokens rather than a single DTCG composite `$value` object (see `tokens/semantic/global/typography.json`) — each sub-property (`fontFamily`, `fontWeight`, `fontSize`, …) is its own ordinary token and already round-trips as a Figma Variable via the existing pipeline. Figma Text Style support (see Planned below) does **not** change that shape. It adds one new, purely opt-in convention: a group may carry `"$type": "typography"` at the **group level** (DTCG's own type-inheritance rule makes this spec-legal) to mark it as something that should *also* be synced as a Figma Text Style, in addition to its children syncing as Variables as they already do. A group without the marker is completely unaffected — existing repos need zero restructuring, only an additive opt-in per style if they want it.
* **Canonical field vocabulary** (`shared/typography-styles.ts`, `TYPOGRAPHY_FIELDS`): `fontFamily`, `fontWeight`, `fontSize`, `lineHeight`, `letterSpacing`, `paragraphSpacing`, `paragraphIndent`, `textCase`, `textDecoration`. The first 7 correspond to Figma's `VariableBindableTextField` (bindable to a Variable — confirmed against Figma's plugin API docs directly: `'fontFamily' | 'fontSize' | 'fontStyle' | 'fontWeight' | 'letterSpacing' | 'lineHeight' | 'paragraphSpacing' | 'paragraphIndent'`); `textCase`/`textDecoration` are real `TextStyle` properties Figma does **not** support binding to a variable — they can only ever be literal.
* **Why not model this as a different token shape per source**: `docs/design/canonical-model.md` already established that source-specific shapes (e.g. Token Studio's single-object composite `$value`) get normalized by their own adapter into one canonical shape before anything downstream sees them. So this feature only ever needs to understand the one decomposed shape natively; a Token Studio-shaped composite typography token is the future Token Studio adapter's problem to expand into this shape on import, not this feature's.
* **Resolved (Stage 0 spike, real Figma file, July 2026): our `fontWeight` field must bind to Figma's `fontStyle`, not `fontWeight`.** A `STRING` variable holding a literal style name (`"Bold"`) bound via `setBoundVariable("fontWeight", …)` throws: *`"variable of resolved type 'STRING' cannot be bound to 'fontWeight'"`* — that Figma field expects a numeric weight axis (variable fonts only), which nothing in this repo's tokens ever produces (confirmed: designers don't observe numeric weights in Figma in practice). `setBoundVariable("fontStyle", …)` succeeded with no error, and — the real proof — the style's resolved `fontName.style` correctly updated to `"Bold"`. So the field-name mapping is **not** an identity map: `TypographyField.fontWeight` → Figma field `"fontStyle"`; every other field maps 1:1 (`fontFamily`→`fontFamily`, `fontSize`→`fontSize`, `lineHeight`→`lineHeight`, `letterSpacing`→`letterSpacing`, `paragraphSpacing`→`paragraphSpacing`, `paragraphIndent`→`paragraphIndent`). This mapping table lives in the Stage 3 write-path code, not in the token format — `$type: "fontWeight"` in token files is unaffected and stays correctly named.
* **Confirmed consequence, found live (September 2026): named weights being `STRING`-typed also broke `inferType()` on the *push* side.** `figma-to-tokens.ts`'s `inferType` had a `STRING` branch that checked `/family|font/i` before anything else — a variable named `fontWeight/light` matches that regex too (it contains "font"), so every named weight got written to the repo as `$type: "fontFamily"` instead of `$type: "fontWeight"`. Pre-existing, but only surfaced once a real push actually included a dedicated `fontWeight/*` primitive file for the first time. Fixed by checking `/weight/i` first, mirroring the `FLOAT` branch just below it, which already did this correctly.
* **Push direction built (September 2026): target file decided — `semantic/global/typography.json`, same file the read/apply direction already targets.** `getLocalTypographyStyles()` (real Figma Text Styles, via `figma.getLocalTextStylesAsync()`) is read on every collection load but was previously discarded before reaching the push flow — `handlePushCollectionsLoaded` only forwarded `collections`/`variables`. Now threaded through (`Sync.tsx` → `sync-logic.ts`'s `buildFilesFromDiffs` → `figma-to-tokens.ts`'s `figmaToTokenFiles`) into a new `injectTypographyStyles` step that overlays each Text Style onto the Variable-derived typography tree: sets the group-level `$type: "typography"` marker (which has no Variable counterpart — it only exists because a matching Text Style does), and writes every field the Text Style reports, unconditionally. Fields are written unconditionally rather than merged because a bound field's value here is already identical to what the matching Variable-derived entry would produce (both resolve to the same `{ref}}`, since Token Spark's own apply flow binds a Text Style field to the *target* of a token's ref, not to an intermediate variable at the group's own path — confirmed by tracing `tryBind` in `figma-text-styles.ts`), and `textCase`/`textDecoration` have no Variable counterpart at all, so they can only ever reach the file through this path. This also makes a Text Style created entirely by hand in Figma (no matching Variables yet) work correctly — the group is created fresh from the style's own fields instead of silently missing every field pushed.
* **Diff visibility built the same day, once asked about directly**: `figmaToCollections` also merges Text Style fields into the Global collection's flat token map (`flattenTypographyStyles`) — the same data the push diff view (`computePushDiff`) already reads for every other token, so a Text Style field change shows up as an ordinary added/changed/removed diff entry with no new UI code needed. This is a genuinely separate code path from `injectTypographyStyles` above (flat `Record<string, TokenValue>` for the diff vs. a nested JSON tree for the file) — both are necessary, not a missed dedup.
* **Known scope boundary, accepted for now**: the group-level `$type: "typography"` marker itself has no equivalent in the flat-path diff model, so a Text Style opting into the marker for the first time (with all-literal fields matching what was already there) wouldn't show as a change — an edge case, since a fresh Text Style normally also introduces new/changed field values, which *do* diff. Matches the same already-accepted limitation on the pull side (`applyTypographyStyles`'s own doc comment: "no diff view exists yet for typography styles to make a deletion reviewable before it happens").

### CSS Deduplication Is Value-Based, Not File- or Metadata-Based
* **Decision**: `css.ts` hoists a token into `:root` instead of repeating it in per-variant blocks whenever that's provably safe from the resolved values alone — no new file convention, no token marking. Two independent cases: (1) a semantic token whose final CSS value is byte-identical between the Light and Dark collections is hoisted out of both `[data-color-scheme]` blocks into `:root`; (2) a non-default theme only emits the variables that actually differ from the default theme (the default theme's own values already populate `:root`) — a non-default theme identical to the default emits nothing and inherits everything via the cascade. Both comparisons run on the fully-resolved value a `TextStyle`/CSS declaration would actually receive, not on `$value` alone and not on any `$type`/metadata marker.
* **Rationale**: this was prompted by the real Coop system (14 themes, see the stress test) that had manually pre-split its semantic tokens into 5 files (`theme-light`, `theme-dark`, `global-light`, `global-dark`, `global`) specifically to avoid writing scheme-invariant values twice. Requiring every adopter to pre-split their files the same way would be exactly the kind of rigid, tool-imposed authoring convention this project has deliberately avoided elsewhere. Detecting invariance from the data instead means it works regardless of how a team chooses to organise their files — one file or many — and it's self-correcting: if a 5th brand later gives a previously-uniform color its own value, the very next build stops hoisting it automatically. A manually-classified "global" file can silently go stale; a value comparison recomputed on every build cannot.
* **Correctness properties, both deliberately verified with tests** (`css.test.ts`): a value must match across **every** relevant variant, not "most" or "at least two" — one theme (or scheme) disagreeing, or simply not defining the token, disqualifies hoisting entirely. And a `{light.*}`/`{dark.*}`-aliased (ref-based) token is *never* hoistable even if it happens to resolve to the same hex in both schemes today — the raw ref differs (`{light.X}` vs `{dark.X}`) by construction, so genuinely theme-aware tokens can never be accidentally collapsed.
* **Known scope boundary, accepted for now**: the theme-axis check only compares each non-default theme against the *default* theme, not every theme against every other. Two non-default themes that happen to agree with each other (but not the default) each still get their own, separately-emitted override — correct output, just not maximally deduplicated. Closing that gap would mean no theme is structurally "the baseline" anymore (`:root` would only hold values *every* theme agrees on, and the current default theme would need its own override block like any other) — a bigger restructuring than what real usage has asked for yet.
* **Also fixed as a side effect**: the non-default-theme CSS block's doc comment has claimed "only what differs from the default theme" since it was first written — the code never actually did that until this change. The comment is now true.

### CSS `var(--*)` References Are Verified Against Real Targets, Never Pattern-Matched on Ref Spelling
* **Decision**: `css.ts` converts a semantic token's `{ref}` into a `var(--*)` reference whenever the *target path actually exists* as a real CSS declaration (a member of primitives + global + the default theme's own paths) — never by matching the ref text against a fixed spelling like `{light.X}`/`{dark.X}`. `resolveSemanticValue` replaces the old `toThemeAwareValue`.
* **Rationale**: the old regex (`/^\{(light|dark)\.[^}]+\}$/`) only matched a ref that starts with `light.`/`dark.` at the top level — this project's own convention. Coop's real data aliases through `{color.light.X}`/`{color.dark.X}`, one path segment deeper, which the regex missed entirely; those tokens fell through to a value that (before the separate reference-resolution fix above) was never resolved at all, and after that fix, resolved to a correct but *static* value — losing live `[data-theme]`/`[data-color-scheme]` switching for exactly the tokens that most need it. There is no reliable *spelling* rule that generalizes safely — matching "light"/"dark" as a path segment anywhere risks a false positive on some unrelated token whose name happens to contain that word. Checking whether the target is a real, referenceable CSS var sidesteps the whole problem: it's not pattern-matching intent, it's confirming the var will actually resolve to something at runtime, using the exact same path → CSS-var-name transform (`toCSSVar`) every other part of this file already uses, so the two can never disagree about spelling.
* **A deliberate, wider consequence**: a semantic token that aliases a *primitive* directly (severity colors — theme-invariant but still genuinely scheme-dependent) now also gets `var(--*)`, not a baked-in literal. This is correct, not just permitted: if the underlying primitive's value ever changes, the semantic role should reflect it, same as it would if a developer had written `var(--color-red-600)` in CSS by hand.
* **Safety property, verified with tests**: a ref whose target *doesn't* actually exist anywhere (e.g. no Themes collection at all) never becomes `var(--*)` — it falls back to the already-resolved literal. A `var()` reference is only ever emitted when it's guaranteed to resolve; the alternative (emitting one that might not) would trade a resolved-but-static value for possibly-broken CSS, which is strictly worse.

### Push Direction Must Actually Resolve References, Not Just `$value`-Copy Them
* **Decision**: `figmaToCollections` (the push/Figma-read path) now builds a genuinely resolved `tokens` map — aliases walked to their final value, exactly like `parseRepository` already does on the GitHub/pull side (primitives → resolve themselves; global/themes → resolve against primitives; semantic → resolve against primitives + the default theme + global). `rawTokens` is untouched — every `{ref}` stays exactly as Figma stored it, for writing token files and for the CSS transformer's `{light.*}`/`{dark.*}` → `var(--light-*)`/`var(--dark-*)` cascade detection.
* **What was actually happening before, found via the Coop stress test**: `figmaToCollections` set `rawTokens: tokens` — literally the same object — with the comment *"Figma values already have refs as {path} strings; raw === resolved in push direction."* That's only true for a variable whose value isn't an alias at all. The moment a variable *is* a `VARIABLE_ALIAS` (the normal, expected way a multi-layer token system is built in Figma — a theme referencing a primitive, a semantic token referencing the theme layer), its value became literal unresolved `{ref}` text with nothing downstream ever resolving it. The CSS transformer's `toThemeAwareValue` only converts the *exact* pattern `{light.X}`/`{dark.X}` at the top level into a cascading `var()` reference; anything else — a theme→primitive alias, or a semantic alias nested one level deeper like Coop's actual `{color.light.X}` — fell through to `resolvedValue`, which was never actually resolved, and got written straight into the generated CSS as an invalid declaration value.
* **Real-world scale of the bug, confirmed by inspecting the actual generated `dist/tokens.css` from the Coop stress test**: 1927 of 3627 lines — more than half the file — were broken, across every block type (`:root`, every non-default theme, all three color-scheme blocks). This wasn't a Coop-specific edge case; it's the normal shape of any real multi-layer token system, and had presumably been masked in this project's own testing because unit-test fixtures and this repo's own light manual testing never happened to exercise a deep alias chain through the push path.
* **What's still a separate, un-addressed limitation, not fixed here**: `toThemeAwareValue`'s exact-match regex for the cascade shortcut. Coop's semantic tokens now resolve to real, valid CSS values — but because their alias shape (`{color.light.X}`) doesn't match the special-cased `{light.X}` pattern, they resolve to a **static value baked in at build time**, not a `var(--light-*)` reference. That means Token Spark's marquee "flip `[data-theme]`/`[data-color-scheme]` and colours update live via the cascade" feature does not work for Coop's data today, even though the CSS is no longer invalid. Generalising that detection (matching `light`/`dark` as a path segment anywhere, not just as the literal prefix) is a real follow-up, deliberately not rushed alongside this correctness fix — it needs a precise rule that can't false-positive on an unrelated primitive whose name happens to contain "light".
* **Scope note**: primitives and global are still merged to a single-mode entity when resolving on push, matching `parseRepository`'s existing assumption on the pull side — this doesn't (and isn't meant to) solve the separate, already-tracked multi-collection-per-role problem (e.g. Coop's `Size` collection). The reported `modeName` is Figma's *real* mode name (the first one encountered), not a fabricated placeholder — see the immediately-following bug this caused.
* **Also fixed, found immediately after shipping the above**: the first version of this fix hardcoded `modeName: "Value"` for primitives/global instead of using Figma's real mode name. That silently broke real pushes: the diff/selection UI is built from this fabricated name, but `buildFilesFromDiffs` (`Sync.tsx`) filters the *original, untouched* Figma collection data by matching `${collectionName}/${modeName}` against what's selected — using Figma's *real* mode name. Since "primitives/Value" never matched "primitives/`<real mode name>`", primitives silently dropped out of the generated PR even though it displayed as selected in the UI. Confirmed against the actual Coop stress test: `tokens/primitives/color.json` was missing from a PR despite never being deselected. See the new Code Invariant below.

### Multiple Figma Collections Per Role + Collection-Mapping UI
* **Decision**: `Metadata.figma.collections` is now `{ primitives: string[]; global: string[]; themes: string[]; semantic: string[]; sizes: string[] }` (see the exported `CollectionNames` type in `token-merger.ts`) instead of one string per role — several physical Figma collections can now back one logical role. A new "Map collections" screen (`CollectionMapping.tsx`, reachable from an action card on `Sync`'s main screen) lists every real Figma collection (from the existing `COLLECTIONS_LOADED` payload — no new plugin message needed) and lets the user assign each to a role or Ignore, writing the confirmed mapping into `metadata.json` via a PR through the same `createTokenPR` the push flow already uses. `sizes` is the fifth role, and — as of the following decision — a real second axis on Primitives, not just a recognized-but-inert placeholder.
* **Rationale**: Figma's one-mode-axis-per-collection constraint forces a real design system into more physical collections than roles — Coop's own library has ~6 collections (`Primitives`, `Size`, `Theme`, `Main Color`, `Support Color`, `Semantic`) for 4-5 logical roles. A one-name-per-role config literally cannot express "Main Color and Support Color together are the Themes role," and hand-editing `metadata.json` names/casing was already an observed real workaround (see the Coop stress test entries above).
* **Read direction (Figma → GitHub) merges automatically**: `collectionKind()` now checks list membership (`.includes()`) instead of exact-string equality, and the existing raw-token accumulator in `figmaToCollections`/`figmaToTokenFiles` already merges everything matching one role together. **One real gap found and fixed while building this**: two physical collections can each contribute a mode with the identical name (Main Color's "Christmas" and Support Color's "Christmas" are meant to be the same logical theme) — the old code treated each `(collection, mode)` pair as its own entry, which would have produced two separate `ResolvedCollection`s both rendering as `[data-theme="christmas"]`, and on the write side, two files written to the same `semantic/themes/christmas.json` path with the second silently overwriting the first. Fixed by merging same-named modes (case-insensitively, first-seen casing wins for display) before resolving/writing — covered by tests in `figma-to-tokens.test.ts`.
* **Write direction (GitHub → Figma) needs one definite target**: token files on GitHub have no record of which physical Figma collection they came from, so `parseRepository` stamps `names.X[0]` — the first configured name — as the canonical apply/create target per role. The rest of a role's list is a read-only additional source, never a write target. Documented inline in `token-merger.ts`.
* **Migration**: a `metadata.json` written before this change still has bare strings for `figma.collections.X`. `parseMetadata` coerces a legacy string into `[string]` and only falls back to the default when the field is genuinely absent or unusable — an explicit empty list (`[]`, meaning "intentionally unmapped") is preserved, not treated as missing. Also added: a `console.warn` (not a throw — a config typo in a plugin sandbox shouldn't hard-fail) if the same Figma collection name is hand-listed under two roles.
* **A second real gap found and fixed (September 2026), more serious than the first: the push *file-selection* step silently dropped every physical collection except one.** Found live: a real project had `figma.collections.primitives = ["size", "primitives"]` — a genuinely multi-mode "size" collection and a single-mode "primitives" collection (colors) both backing the role. The push diff correctly *showed* both collections' tokens merged into one entry (`figmaToCollections` already handled the merge, per the decision above) — the user checked it, created the PR, and the color primitives were simply never in the resulting file. Root cause: `buildFilesFromDiffs` (`sync-logic.ts`) filtered `figmaRaw.collections` by matching `selectedKeys` (built from the *synthetic* merged name, e.g. `"size/mobile"`) against each **real** physical collection's own name (`"primitives"`, which never appears in `selectedKeys` at all) — so only the one physical collection whose real name happened to equal `figma.collections[role][0]` ever survived the filter, and every other collection sharing that role was silently dropped, even though it was checked and counted in the PR the user approved. Fixed with a new `isModeSelected` helper that re-derives each real (collection, mode) pair's role via `collectionKind()` (now exported) and matches against the synthetic key the same way `figmaToCollections` builds it: primitives/global are all-or-nothing per role (the diff never lets you pick apart what's already merged into one entry), themes/semantic/sizes match by mode name case-insensitively (mirroring `mergeIntoMode`). Two regression tests reproduce this exactly — the primitives case above, and the pre-existing "Main Color"/"Support Color" Christmas-mode case from the decision above, run all the way through `buildFilesFromDiffs` this time instead of stopping at `figmaToTokenFiles` — both confirmed to fail without the fix.
* **Why the original multi-collection tests didn't catch this**: they called `figmaToTokenFiles` directly (see the decision above), which correctly merges multiple physical collections — that logic was never wrong. The bug lived one layer up, in `buildFilesFromDiffs`'s selection filtering, which sits *before* `figmaToTokenFiles` and was never exercised by those tests at all. A correctly-tested unit two layers down doesn't guarantee the layer that calls it passes it the right input — worth remembering next time a "this is already tested" assumption is made about multi-collection-role code.
* **A fourth occurrence, found live after everything else above was already fixed and verified: `computePullDiff`'s Figma-side lookup had the identical class of bug, and it's the most user-visible one.** Symptom: after a completely clean repo wipe and fresh push, pulling straight back still showed every color token as "added" — not "changed," genuinely *added*, as if Figma had nothing at those paths at all, immediately after pushing those exact values from Figma. Root cause: `computePullDiff` matched a GitHub role's merged entry (e.g. `"size"`, `collections.primitives[0]`) against Figma's flat value maps via `figmaMaps.find(m => m.collectionName === githubCol.collectionName && ...)` — an exact-name `.find()` that can only ever return one `FigmaFlatMap`, so for a role backed by two physical collections, tokens living in the *other* one (colors, in `"primitives"`) could never be found, no matter how many times the repo was pushed and re-pulled. Fixed with `figmaValuesFor`, which filters (not finds) every `FigmaFlatMap` whose real collection shares the GitHub entry's role — via `collectionKind`, same as `isModeSelected` — and merges all their values together; primitives/global merge regardless of mode (mirroring how `figmaToCollections` already flattens them on the GitHub side), themes/semantic/sizes match by mode name case-insensitively. Regression test reproduces the exact live scenario and is confirmed to fail without the fix.
* **Why this one is the most consequential of the four**: the other three affected getting data *into* the repo correctly (push selection, apply routing). This one affected whether the *diff view itself* — the thing a user reads to decide whether anything actually needs applying — was ever telling the truth for a multi-collection role. A repo that was byte-for-byte identical to Figma still showed thousands of false "added" entries every single pull.
* **A fifth occurrence, qualitatively different from the first four: an entry can be a genuine composite of two roles, and every one of the four fixes above assumed exactly one.** Found live, immediately after the fourth fix: mapping a genuinely multi-mode Size collection to the dedicated `sizes` role (the fix for it being incorrectly folded into `primitives` — see the Size axis decision) still resulted in zero `primitives/sizes/*.json` files reaching a push PR no matter what was checked in the diff. Root cause: `figmaToCollections`/`parseRepository` both build a Size-mode `ResolvedCollection` as `{...primitivesRaw, ...sizeModeRaw}` — shared primitives merged with that mode's own data — always labeled `collectionName: names.primitives[0]`, **never** `names.sizes[0]` (sizes is a second axis *on* primitives, not an independently displayed role — confirmed this is deliberate: the Size axis's own tests explicitly assert colors are present inside every size mode's `ResolvedCollection.tokens`). All four fixes above derive a single `CollectionKind` from an entry's `collectionName` via `collectionKind()` — for a size-mode entry that's always `"primitives"`, never `"sizes"` — so `isModeSelected` was checking for a `"size/mobile"` selection key that can never exist (the real key is always `"primitives/mobile"`), and `figmaValuesFor`/`resolveTarget` had the equivalent gap for pull comparison and apply routing.
* **A "clean separation at the source" fix was seriously considered and rejected.** The obvious-looking alternative — make `figmaToCollections`/`parseRepository` stop merging, expose one clean shared-primitives entry plus separate filtered per-size-mode entries, matching how Global/Themes/Semantic already only expose their own filtered tokens — turned out to have a much bigger blast radius than it first appeared: `css.ts` (and the identical pattern in `js.ts`/`dart.ts`/`swift.ts`) picks one "default primitives mode" from `metadata.sizes` order and treats every *other* `Primitives`-named entry as a media-query override containing the *full* data set. Splitting shared and size-specific data into separate entries would make the plain shared-primitives entry look like a stray extra size mode to that logic and get incorrectly wrapped in a `@media` guard — colors would then only apply above/below a breakpoint instead of unconditionally. Fixing that would mean *also* touching 4-5 transformer files that are stable, already correct, and untouched by any of today's bugs — a big risk to core-adjacent working code for a benefit that's largely cosmetic, since the *committed JSON files* were never actually wrong (`figmaToTokenFiles`/`buildSizeFile` already write clean, separate `primitives/sizes/{mode}.json` files today, confirmed by direct read — none of these five bugs ever affected what actually lands in the repo, only the diff/selection/apply-routing logic reasoning about it).
* **Fixed instead by widening the `primitives` branch in the same four functions**: a `"primitives"`-labeled entry's real Figma counterpart is now understood as the union of every real `primitives`-role collection (unconditionally — shared, identical regardless of mode) plus every real `sizes`-role collection whose own mode name matches the entry's mode name (mode-specific). `isModeSelected` and `figmaValuesFor` merge both directly; `resolveTarget` checks `sources.primitives` and `sources.sizes` for a segment before falling back. No other role needed this — `"sizes"` never appears as an entry's own resolved role in the first place. Three new regression tests reproduce the exact live shapes (selection, pull comparison, apply routing), each confirmed to fail without its fix. See "Core Priorities" at the top of this document — this is the incident that prompted writing that section.

### `parseRepository`'s Theme/Global/Semantic Resolution Context Must Deep-Merge, Not Shallow-Merge
* **Decision**: `token-merger.ts`'s `mergeTrees` (shallow — a later tree's top-level key completely replaces an earlier tree's key of the same name) is gone entirely. Every call site that combined `defaultPrimitivesTree` with a Global/Theme/Semantic tree — the four places building each collection's reference-resolution context — now uses the already-existing `deepMergeTrees` instead, exactly the same function `layers.primitives`' own multi-file merge already used.
* **Found live, directly contradicting Core Priority #4 ("references resolve correctly"), and severe: 2238 diff entries across every one of 14 real themes showed as "changed" on a push where nothing had actually changed in Figma.** Root cause, confirmed by executing the real `parseRepository()` against real fetched repo data (not a simplified re-implementation — a prior Python-based reference check had missed this exact class of bug, since it only asked "does this literal path exist as a leaf anywhere," not "does it exist in the actual merged context `resolveAllReferences` runs against"): a real theme file (`semantic/themes/masterbrand.json`) nests its `light`/`dark` groups under a top-level `"color"` key — the *same* top-level key `primitives/color.json` uses. `mergeTrees([defaultPrimitivesTree, themeTree])` is a shallow, top-level-key merge: `themeTree`'s own `"color"` key completely overwrote `defaultPrimitivesTree`'s `"color"` key in the merged result, instead of merging into it — silently deleting every primitive color (204 of them, confirmed) from the context available to resolve that theme's own refs. A ref like `{color.blue.950}` then had nothing to resolve against, and `resolveReference`/`resolveAllReferences`'s existing "fall back to the original unresolved literal on a miss" behavior (by design, for genuinely broken refs) masked it as if the reference were simply broken, when the primitive was correctly defined all along.
* **Why this was invisible until now**: every existing test fixture's theme/global/semantic top-level keys (`light`, `dark`, `background`, `text`) happened not to collide with the primitives fixture's own top-level keys (`color`), so the shallow merge behaved identically to a deep merge in every test — the same "coincidental non-collision masks a real bug" pattern as several fixes above. The collision only became likely once primitives were reorganized into one real file per category (`color.json`, `fontFamily.json`, `fontWeight.json` — see Core Priority #3, "clean, team-usable JSON") *and* a real theme file's own natural group name is also `"color"`, which is the common case, not an edge case — this bug was latent for as long as primitives were one compounded file with no single dominant top-level key to collide on.
* **Scope**: affected the Global, Themes, and Semantic resolution contexts equally (`globalWithPrimitivesFlat`, `fullFlatUnresolved` for themes, and both `rawFlatUnresolved`/`resolvedFlat` for semantic all built via the same shallow `mergeTrees`) — Themes was simply the first to have a real top-level key collision surface it. `layers.primitives`' own multi-file merge (`deepMergeTrees(Object.values(layers.primitives))`) was never affected — it already used the deep version.
* **Test coverage**: new regression test in `token-merger.test.ts` reproduces the exact live shape (a theme file with a top-level `"color"` key referencing a primitive also under `"color"`), confirmed via git-stash to fail without the fix.

### Global's Resolution Context Now Includes the Default Theme — Type Styles Reference a Theme-Scoped Group, Not Primitives Directly
* **Decision**: `parseRepository`'s Global collection now merges the default theme's tree into its *resolved* value computation (`globalResolved`), exactly mirroring what Semantic already did. `rawTokens` (`globalRawUnresolved`) is unaffected — still just Primitives + Global's own tree, no theme — since that field is what Figma alias creation reads and must keep the ref as a literal, not bake in one theme's answer.
* **Found live, immediately after re-verifying the deep-merge fix above against a fresh push**: 54 unresolved refs, all in Global's `typography.*` fields (`{font-family.display}`, `{font-weight.display.bold}`, …) — same failure mode as the deep-merge bug (a diff showing false "changed" on every push), different root cause. The user clarified the real reference chain, matching both the live Figma structure and Token Studio's own repo shape: `fontFamily (Primitives) → Theme (e.g. Masterbrand) → type styles`. A theme picks its own named font/weight (`font-family.display`, `font-weight.display.bold`, …) and a type style (written to `semantic/global/typography.json`, the Global role) references *that* theme-scoped choice — never Primitives directly. Global's resolution context, unlike Semantic's, never merged in any theme tree at all, so these refs had nothing to resolve against no matter how correctly the theme file itself was structured.
* **Why the "Global" label doesn't have to change**: type styles still live at the same file path (`semantic/global/typography.json`) and same role — this fix only widens what Global's *display/diff* value is computed against, matching the precedent Semantic already set (its own resolved value also substitutes the default theme, and switching themes doesn't change which value Semantic's diff shows either — an accepted, pre-existing simplification, not a new one introduced here). No file layout change, no apply-side change: `rawTokens` (what actually gets used to create Figma aliases on pull) keeps the literal ref untouched.
* **Live CSS output was not affected by this specific gap** — `runTransformers` generates CSS from Figma's own live data at push time (`figmaToCollections`), not from `parseRepository`'s GitHub-read side; only the GitHub-side "resolved" value used for push-diff comparison was ever wrong. Confirmed by reading `sync-logic.ts`'s `buildFilesFromDiffs` call site before concluding this was diff-only, not a CSS-correctness bug too.
* **Test coverage**: new regression test in `token-merger.test.ts` reproduces the exact live shape (Global token referencing a theme-scoped `font-family.display` group), confirmed via git-stash to fail without the fix.
* **Correction, found immediately after this shipped: the "CSS output was not affected" claim above was wrong — `figmaToCollections` (the Figma/push side) had the *identical* gap, and that one genuinely does feed CSS.** See the next decision below.

### `figmaToCollections` Needed the Identical Default-Theme Fix — the Push Side Has the Same Gap as the Pull Side
* **Decision**: `figma-to-tokens.ts`'s `figmaToCollections` now merges `defaultThemeRaw` into Global's resolved-value computation, exactly mirroring the `parseRepository` fix directly above. `defaultThemeRaw` (previously computed just before the Semantic loop, only for Semantic's own use) moved earlier, right after `defaultPrimitivesRaw`, so Global can use it too — Semantic's own usage is unchanged, just no longer duplicated.
* **Found live from the user's own push-diff screenshot**, immediately after the pull-side fix above was verified: `banner.fontFamily` showed `Coop Sans` (GitHub, now correctly resolved) on one side and the literal `{font-family.display}` on the other — that other side is Figma's own live value, not GitHub's. Root cause, confirmed by reading `figmaToCollections` directly: its Global resolution (`resolveAllReferences({ ...defaultPrimitivesRaw, ...globalRaw })`) never merged in any theme raw data either — the identical gap as `parseRepository`'s, just on the opposite side of the sync. Before the pull-side fix, both sides happened to show the same unresolved literal, which looked like "no diff" — not because the reference resolved correctly, but because *both* sides were equally broken. Fixing only the pull side unmasked the push side's matching gap, the same "coincidental match hides a real bug" pattern documented several times above (e.g. the shallow-merge fix), just one level up: this time a *fix* unmasked a *sibling* bug instead of a test fixture accidentally avoiding a collision.
* **This one does feed real output, unlike the pull-side gap**: `runTransformers` (the CSS/JS/Dart/Swift generator) is called with `figmaToCollections`'s output directly, and `css.ts`'s `:root` block spreads `global?.tokens` straight into the generated stylesheet. A real push before this fix would have emitted the literal `{font-family.display}` text as a CSS custom property value — invalid CSS — for every type style whose font/weight referenced a theme-scoped group. This corrects the "live CSS output was not affected" claim in the previous decision entry, which was true only for the *pull*-side gap, not this push-side twin.
* **Test coverage**: new regression test in `figma-to-tokens.test.ts` reproduces the exact live shape (a Text Style field bound to a Theme-collection Variable that itself aliases a Primitives Variable), confirmed via git-stash to fail without the fix.

### FLOAT Variables Named "dimension" Were Misclassified as Plain Numbers, Losing Their Unit on Every Push
* **Decision**: `inferType`'s FLOAT-classification regex now includes `dimension` itself: `/dimension|size|spacing|padding|radius|width|height|border|gap/i`.
* **Found live from the same push-diff investigation, a separate report from the same message**: the user also flagged that pulling showed every `primitive.dimension.*` value as permanently "changed" — Figma's live value `"0px"`/`"3px"`/… against GitHub's stored bare `"0"`/`"3"`/… (no unit). Root cause, confirmed by reading the real committed `primitives/sizes/mobile.json`: these variables were written with `$type: "number"`, not `$type: "dimension"` — `rawToTokenValue` only appends `"px"` when `$type === "dimension"` (§1 line ~615), so a `"number"`-typed value like this stays a bare digit string forever. `inferType`'s FLOAT branch decides `dimension` vs `number` purely by keyword-matching the variable's own name against `size|spacing|padding|radius|width|height|border|gap` — and a variable literally named `dimension/0` matches *none* of those keywords, since none of them is a substring of "dimension" itself. Ironic but real: the most literally-named case was the one the regex forgot.
* **Why this was invisible until now**: every existing test fixture used names like `font-size/1` (matches `size`) — nothing exercised a variable named exactly `dimension`, which is Coop's own real naming convention for its base spacing/sizing scale, not a hypothetical.
* **A stale test assertion baked in the bug as "expected" and had to be corrected, not just left passing**: `sync-logic.test.ts`'s Primitives+Sizes composite test used a variable named `primitive/dimension/1` and asserted its written value was `"4"` — coincidentally exercising the exact misclassification and then asserting the *buggy* output as correct. Fixed to assert `"4px"`, the actually-correct value now that the type infers correctly.
* **Test coverage**: new regression test in `figma-to-tokens.test.ts` (`figmaToTokenFiles — FLOAT variable type inference`) proves a FLOAT variable named `dimension/0` writes `$type: "dimension"` and a `"4px"`-shaped value, confirmed via git-stash to fail without the fix.

* **Decision**: `token-merger.ts` gains two new, purely additive exported helpers — `findGlobalCollection(collections, names)` and `selectDefaultPrimitives(collections, metadata)` — used only by the five output-generation files (`css.ts`, `js.ts`, `dart.ts`, `swift.ts`, `transformer/index.ts`). Nothing in the sync/diff/apply pipeline (`sync-logic.ts`, `figma-to-tokens.ts`, `token-diff.ts`, `useFigmaValues.ts`) was touched — `collectionKind()` and every function built on it keep their exact existing behavior.

* **Confirmed zero effect on push/pull**: the diff for this PR touches only `token-merger.ts` (new, additive exports) and the five transformer files (an internal lookup swap) — `sync-logic.ts`, `figma-to-tokens.ts`, `token-diff.ts`, and `useFigmaValues.ts` have zero changes. ### `resolveReference` Now Detects Circular Aliases Instead of Crashing With a Stack Overflow
* **Decision**: `token-format.ts`'s `resolveReference` gains a third, internal-only `chain` parameter (a list of paths visited in the current resolution) — a `{ref}` whose path is already in `chain` is treated as unresolvable (warns via `console.warn` with the full chain shown, returns `null`, exactly like an already-established "missing token" miss) instead of recursing again. Both the pure-ref branch and the embedded-ref (composite value) branch are covered. `resolveAllReferences` and every other caller are unaffected — the parameter defaults to `[]` and is never meant to be passed explicitly from outside this file.
* **Found by comparing against a mature, real-world reference implementation** — a production Flutter app's Token Studio → Dart codegen pipeline (unrelated codebase, reviewed at the user's request for transformer ideas) — whose own reference resolver explicitly tracks the resolution chain and throws a clear, actionable error naming the exact cycle the moment one is detected. Our own `resolveReference` had **no depth guard or cycle detection of any kind**: a circular alias (`a: "{b}"`, `b: "{a}"` — plausible from a bad hand-edit or a bad merge, not just a contrived case) would recurse until Node's call stack overflowed, crashing with an opaque `RangeError: Maximum call stack size exceeded` instead of a targeted, debuggable message pointing at the actual broken tokens.
* **Scope check before fixing**: confirmed no math-expression-style token values (`{ref} * 2`, `floor(...)`, etc. — a real Token Studio capability the same reference implementation explicitly evaluates, which this project's `resolveReference` doesn't attempt at all) exist anywhere in the real Coop stress-test data today — a real gap in principle, filed under the not-yet-built "Token Studio adapter" backlog (§4 Priority 1b), but not an active one for this project, so left untouched here rather than folded into this fix.
* **Why "warn and fall back" instead of throwing**: matches this codebase's own established convention for "can't resolve this" (`warnOnDuplicateCollectionNames`'s doc comment: "a plugin sandbox shouldn't hard-fail on a config typo") — a circular reference is a data problem, not a reason to crash the whole plugin. The literal `{ref}` string survives unresolved, same as any other unresolvable reference, just now with a console warning instead of silent (or crashing) failure.
* **Test coverage**: 4 new tests in `token-format.test.ts` — a direct 2-hop cycle, a longer 3-hop cycle, a cyclic embedded ref inside a composite value, and a non-cycle control case (the same shared primitive referenced by two independent, non-looping tokens, which must still resolve normally). Confirmed via git-stash that all 3 cycle tests fail with the exact `RangeError: Maximum call stack size exceeded` this fix eliminates.

### A Malformed `$value` Anywhere in the Resolution Chain Crashed the Whole Plugin With No Visible Error
* **Decision**: `resolveReference` (`token-format.ts`) now checks `typeof ref !== "string"` at the top and returns `null` — the same "target unresolvable" fallback already used for a missing path or a circular reference — instead of calling `.match()` on whatever it was given. Separately, `handlePushCollectionsLoaded`/`handlePullCollectionsLoaded` (`Sync.tsx`) now wrap their entire synchronous diff-calculation block (`parseRepository`/`figmaToCollections`/`computePushDiff`/`computePullDiff`) in a `try`/`catch` that reports failure via `setStatus({kind: "error", ...})`, exactly like every other GitHub call in this file already does — this block was the one exception to that pattern.
* **Found live testing a second, structurally different design system (Vy's Spor) for the first time** — pushing hung forever on "Calculating diff…" with no error. The browser console showed an uncaught `TypeError: Cannot read properties of undefined (reading 'match')` inside the plugin's own bundled code, traced to `resolveReference`'s `ref.match(...)` at the top of the function — meaning some token's own `$value`, somewhere in a real resolution chain over Spor's live Figma data, was not a string. Every value-construction site this project controls (`rawToTokenValue`, `buildFlatTokens`, `flattenTokens`) was checked and is exhaustive/guarded already, so the exact upstream shape that produces a malformed `$value` couldn't be pinned down without the real Figma file — but `resolveReference`'s own job is precisely "handle a value that might not cleanly resolve," so guarding its own input the same way it already guards a missing path or a cycle is correct regardless of the exact root cause.
* **The real user-facing bug wasn't the crash itself — it was that nothing caught it.** `handlePushCollectionsLoaded`/`handlePullCollectionsLoaded` run entirely synchronously with no try/catch, unlike `handlePush`/`handlePull` and every other GitHub-fetch step in the same file, which all report failure through `setStatus`. Any exception here — this one, or a different one in the future — left the UI permanently stuck on "Calculating diff…" with zero feedback, indistinguishable from a genuine hang. The try/catch fix is the general-purpose one: it makes *any* unexpected exception in this block surface as an ordinary, dismissable error instead of a silent freeze, independent of whether the `resolveReference` guard above happens to cover every future malformed-data shape.

### `PushDiff` Had No Way to Show a Failed PR Creation — a Real Failure Looked Identical to the Button Doing Nothing

### An Unbound Text Style Field Silently Clobbered a Real Variable-Derived Alias, With Zero User-Initiated Change
* **Decision**: `figma-to-tokens.ts` gains `shouldTypographyFieldWin(existing, incoming)` — a Text-Style-derived typography field only overlays onto whatever the Variable-derived tree already has at that path when either nothing exists there yet, or the incoming value is itself a genuine `{ref}` (checked via `token-format.ts`'s new `isPureRef`). Applied in both places a Text Style field gets merged onto Variable-derived data: `figmaToCollections`'s Global flat-map merge (feeds the push diff) and `figma-to-tokens.ts`'s `injectTypographyStyles` (feeds the committed file) — previously both overwrote unconditionally.
* **Found live** (`tokensync-coop-stresstest` PR #35): pushing with zero deliberate changes still produced a diff — `typography.banner.fontSize`'s `$value` had gone from a real alias, `{primitive.font-size.11}`, to a baked literal, `"48"`. Confirmed via the actual PR diff. Root cause: `getLocalTypographyStyles` reads a field as a literal (`readLiteralField`) whenever Figma reports it as *not currently bound* — and on this particular read, `fontSize` came back unbound with no corresponding user action, while `fontFamily`/`fontWeight` on the same style round-tripped fine. The overlay then unconditionally wrote that fallback literal over the real, correct alias already sitting in `globalRaw`/the committed file — destroying live size-axis switching for that token with nothing to review or undo.
* **Deliberately not chasing why Figma reports a field unbound with no user action** — that would require deeper research into `boundVariables` read timing/consistency in the Plugin API, out of scope here. The fix instead makes the overlay itself non-destructive regardless of *why* a spurious unbind read happens: a literal is only ever allowed to fill in where nothing existed, never to replace a real reference. This is the same "don't destroy information you can't get back" stance the Stage 3 apply decision already takes for typography styles removed from the source repo.
* **A genuine, accepted trade-off**: if someone deliberately detaches a field's binding in Figma and sets an intentional literal, that edit is now silently *not* synced, since `existing` (the old alias) is still present and the incoming value isn't a ref. Accepted because the reported failure mode — a completely spurious, no-action diff appearing on every affected typography field — is both the common case and actively erodes trust in the diff view, while a deliberate unbind-to-literal edit is a rare, unusual workflow; nothing prevents editing the token directly in the repo if that's genuinely wanted.
* **Fixes the diff, not just the file**: `figmaToCollections`'s Global merge feeds `computePushDiff` directly, so protecting `globalRaw` there means the push-diff screen itself stops showing a "changed" entry for this token, not just the eventually-committed JSON — the same underlying map serves both.
* **Test coverage**: 2 new tests in `figma-to-tokens.test.ts` — one exercising `figmaToCollections`'s diff-feeding path, one exercising `figmaToTokenFiles`'s file-writing path — both reproducing the exact PR #35 shape (a real alias, an incoming literal at the same path) and confirmed via git-stash to fail with the exact live symptom (`"48px"` instead of the alias) without the fix. All 24 existing tests in the file pass unmodified — none of them had an existing Global-role Variable at the same path as a Text Style field, so `shouldTypographyFieldWin`'s `!existing` branch always applied and behavior is unchanged for every previously-covered shape.

### A "Ghost" Variable Alias — Right Name in Figma's Picker, Dead Target Id — Was Silently Dropped With Zero Trace
* **Decision**: `figma-to-tokens.ts`'s `buildFlatTokens` now returns `{ tokens, brokenAliasPaths }` instead of a bare flat map. When `rawToTokenValue` returns `null` specifically because the raw value is a `VARIABLE_ALIAS` whose target id isn't in `varById` (`isBrokenAlias`), the path is collected into `brokenAliasPaths` instead of vanishing silently. `figmaToCollections`'s result gains a `brokenAliasPaths: string[]` field (same shape as the existing `unknownCollectionNames`), threaded through `Sync.tsx` into a new `PushDiff` warning banner, styled and worded identically to the existing "unrecognized collection" one.
* **Found live** (Vy's Spor system, after a clean-repo wipe ruled out stale diff-comparison state as the cause): dozens of status-color fields (`success`, `notice`, `service`, etc.) were completely absent from every synced output — not broken-but-visible like a dangling `{ref}` string, but entirely missing, no key, no trace anywhere. Two wrong hypotheses were ruled out first, in order: (1) a Figma collection-mapping gap — ruled out, the user confirmed via Figma's own variable picker that these are ordinary variables in the already-correctly-mapped "Theme" collection; (2) team-library-sourced variables, invisible to `getLocalVariablesAsync()` by Figma API design — ruled out, the user confirmed every one of these was created locally in the file, not imported from a library. The user's own follow-up investigation found the real cause directly: a "ghost" alias — Figma's variable picker still displays the correct, intended target name, but the alias's internal target id no longer resolves to any real variable (the target was deleted and recreated, or similar, without the alias being repointed). `rawToTokenValue`'s existing `if (!target) return null` is the *correct* response to this (Token Spark has no way to know what the intended value should be) — the actual bug was one level up: `buildFlatTokens`'s `if ($value === null) continue` treated "genuinely no value" and "alias target is dead" identically, dropping the whole field with nothing left behind to even suggest something was wrong.
* **Why this was so hard to diagnose live**: unlike a broken `{ref}` string surviving into generated CSS (visible, if you know to grep for it — see the Text Style overlay decision above), a dropped Figma *variable* leaves nothing in any output at any layer — not the diff, not the committed file, not generated CSS. The only way to find it was directly inspecting the real Figma variable in the picker, which is exactly what a data-integrity issue *inside Figma itself* requires — but nothing pointed the user toward checking that in the first place.
* **This is now the third confirmed case for the "advisor" surface direction** (§4) — a broken reference silently producing wrong-looking-fine output instead of a visible signal. This fix doesn't build that general mechanism; it reuses the existing, narrower `unrecognizedCollections`-style warning banner pattern, which is sufficient for this one case and doesn't block on that larger, unscoped direction.
* **Scope, deliberately narrow**: only `figmaToCollections` (feeds the push-diff review, the earliest point a user would see this) is fixed. `figmaToTokenFiles`'s `buildJsonFile` has the structurally identical `if ($value === null) continue` and would independently drop the same field when actually writing the committed file — not separately instrumented, since by the time a push reaches file-writing, the same underlying Figma data has already been surfaced (or not) via the diff-review warning above; duplicating the check there would warn about the same broken link twice from the same push. Revisit if `figmaToTokenFiles` is ever called on a path that doesn't go through `figmaToCollections` first.
* **A genuine, accepted trade-off**: Token Spark cannot fix a dead link inside Figma's own variable data — the target could be anything, and guessing would be worse than reporting nothing. The fix's only job is visibility: turn "silently absent, indistinguishable from never having existed" into "reported by name, so a human can go re-link it in Figma."
* **Test coverage**: 3 new tests in `figma-to-tokens.test.ts` reproducing the exact live shape — a ghost alias reported and excluded from tokens; a variable with no value at all for that mode correctly *not* reported (not every "no value" case is a broken alias); a genuinely working alias correctly not reported. All 27 existing tests in the file pass unmodified. Confirmed via git-stash that all 3 new tests fail (`brokenAliasPaths` is `undefined`) without the fix.

### Two Real Figma Variable Names Colliding Structurally Silently Corrupted or Destroyed a Whole Group's Data
* **Decision**: `figma-to-tokens.ts`'s `setNested` (the nested-tree builder `buildJsonFile` uses) now detects when a shorter path already claimed a position as a complete leaf while a longer path tries to nest further under it, or vice versa — and refuses the losing write instead of silently corrupting the tree. It returns `false` when a write is skipped this way; `buildJsonFile` collects these into a `conflictPaths: string[]`, threaded up through all five file-builder functions, `figmaToTokenFiles` (now returning `{ files, conflictPaths }` instead of a bare array), and `sync-logic.ts`'s `buildFilesFromDiffs` (now `{ files, conflictPaths }` too). `Sync.tsx`'s `handleCreatePR` treats a non-empty `conflictPaths` as a hard stop — it throws before ever calling `createTokenPR`, surfaced through the `createError` banner built for the previous decision (*`PushDiff` Had No Way to Show a Failed PR Creation*), rather than letting a known-corrupted write reach GitHub.
* **Found live** (Vy's Spor system, immediately after the ghost-alias fix above): a push reported "6 diffs" the user hadn't made — `surface.brand.default`/`.active`/`.hover`, shown as newly *added*, when `brand` had "always been a group, not a flat value" in Figma. Direct inspection of the committed `vy.json` showed `surface.brand` as a single flat `{$type, $value}` leaf, with the group's `default`/`active`/`hover` completely missing — meaning a *different*, standalone Figma variable literally named `Light/surface/brand` had existed at some point alongside the three group variables (`Light/surface/brand/default` etc.) — both legal, real Figma variable names, but structurally impossible to represent simultaneously in one nested JSON tree. Root-caused precisely with a standalone reproduction of `setNested`'s exact old logic: `typeof current[keys[i]] !== "object"` treats an *already-complete* leaf object (`{$type, $value}`) as an equally-valid "container to walk into," so whichever variable Figma happened to return **last** always won outright — the flat one last means the group vanishes with nothing left behind; the group last means a corrupted hybrid object with both `$value` *and* child keys results. Genuinely non-deterministic-*seeming* from the outside, but fully deterministic given Figma's own variable return order — confirmed by reproducing both orders directly in Node before writing the fix.
* **Why this gets a hard stop, not just a warning banner (unlike the ghost-alias fix above)**: a ghost alias just means one field's value is missing — the rest of the file is still correct and safe to commit. A structural collision means the *file itself* is either missing an entire group's worth of real data or contains a genuinely invalid, ambiguous shape — committing it either way would be worse than not pushing at all. `figmaToCollections`'s flat `Record<string, TokenValue>` (plain string keys, no nesting) has no equivalent failure mode at all — this is exclusively a `figmaToTokenFiles`/`buildJsonFile` tree-construction problem, the opposite scope from the ghost-alias fix.
* **A genuine, accepted trade-off**: Token Spark cannot know which of the two colliding names is the "real" one the team wants to keep — that's a Figma-side naming decision (rename or delete the stale/legacy variable), not something safe to guess at silently. The fix's only job is refusing to proceed with a write that's already known to be wrong, and naming exactly which paths collided so the fix in Figma is obvious.
* **Test coverage**: 3 new tests in `figma-to-tokens.test.ts` reproducing the exact live shape in both possible Figma return orders — never produces a hybrid leaf-and-group object in either order; reports the losing path in `conflictPaths`; a genuinely non-colliding pair of variables reports nothing. All 232 tests in the full suite pass; every test-file caller of `figmaToTokenFiles`/`buildFilesFromDiffs` updated to destructure `{ files }` from the new result shape (a type-only, mechanical change — none of their own assertions changed).
* **Follow-up, same day, asked directly by the user**: "should this be caught by the diff and show which tokens are failing?" — yes. The hard stop above only fires at "Create PR" time, against whatever the user has actually selected; nothing surfaced a conflict *while reviewing the diff*, so a user could review, select collections, and only discover the problem after clicking through. `Sync.tsx`'s `handlePushCollectionsLoaded` now also calls `figmaToTokenFiles` against the full, unfiltered Figma data (mirroring exactly how `unrecognizedCollections`/`brokenAliasPaths` are already computed proactively there, not just at PR-creation time) and stores its `conflictPaths` as new state, rendered as a `tone="danger"` `PushDiff` banner — one severity level above the ghost-alias `tone="warning"` banner, since this one genuinely blocks the push rather than just missing one field. The `handleCreatePR` hard stop stays exactly as built — it's the authoritative check against the *selected* subset, which can differ from the full data if the user deselects the affected collection; the diff-screen banner is a proactive heads-up computed from everything, not a replacement for it. No new unit tests — this is pure UI wiring surfacing data `figmaToTokenFiles` already computes and PR #21 already tests; verified by `npm run typecheck`/`npm run build`/the full suite (232 tests, unaffected) passing.
* **A second follow-up, minutes later**: the user tested the live conflict banner and reported it "was not intuitive enough," plus asked for expandable alerts for long text generally. Reading `StatusBanner.tsx` found the actual bug: its `title` prop renders as a bare HTML `title` attribute — a *hover-only native tooltip* — and all three of `PushDiff`'s new warning banners (`unrecognizedCollections`, `brokenAliasPaths`, and this one) had put their entire actionable guidance there. The always-visible text just said something happened; the part explaining *what to do about it* was invisible unless a user happened to hover — nothing on screen even hinted there was more to read. `StatusBanner` gains a new `expandableDetail?: ReactNode` prop — a "Show details" text toggle (component-local `useState`) that reveals extra content on click, rather than a hover a user has no reason to try. All three `PushDiff` banners were rewritten: the always-visible line is now a short, plain-language summary; the full guidance and path list live behind the toggle. Paths are also now converted through `toFigmaVarName` before display (a new `asFigmaNames` helper) — this project's internal dot-notation (`Light.surface.brand`) isn't what a user sees in Figma's own variable picker (`Light/surface/brand`), so showing dots forced a mental translation step just to go find the variable. The `handleCreatePR` hard-stop error text got the same slash-notation and plain-language treatment. Checked for the same `title`-hides-guidance mistake elsewhere in the codebase (`grep` for every other `StatusBanner` usage with a `title` prop) — these three were the only occurrences. No new unit tests (pure UI wiring/component API addition); verified by `npm run typecheck`/`npm run build`/the full suite (232 tests, unaffected) passing, and a manual read-through of the final JSX in both changed files — a live interactive check wasn't run, since reaching this screen with real conflict data needs the Figma plugin sandbox context, not something a standalone dev-server preview exercises.

### Pull's Own Color-Alpha Conversion Diverged From Push's at One Specific Rounding Boundary
* **Decision**: `useFigmaValues.ts`'s `rgbaToHex` (pull-only — the Figma-side value builder `buildFigmaFlatMaps`/`buildModeMap` uses, feeding both `values` and `rawValues` via `resolveValue`/`resolveOneHop`) now formats a translucent color exactly the way `figma-to-tokens.ts`'s `rawToTokenValue` already does on the push side: hex only when fully opaque, otherwise a decimal `rgba(r, g, b, a.toFixed(2))` string with alpha never quantized through an 8-bit byte. Previously it always produced hex, converting alpha via `Math.round(a * 255)` first — a lossy round-trip push's own conversion never performs at all.
* **Found live** (Vy's Spor system, immediately after the two fixes above): a pull reported the exact same 2 tokens — `Black.25`/`White.25` (alpha 2.5%), formerly named `Black Alpha 25`/`White Alpha 25` — as changed on every single retry, while every other color in the same "foundation" primitives collection (~100 others, all opaque or at other alpha percentages) correctly showed unchanged. Push, reading the identical live Figma data through its own separate conversion path, correctly reported the whole collection up to date. Renaming the two tokens (ruling out anything keyed by name) and confirming directly in Figma that the collection has exactly one mode (ruling out the multi-mode "last write wins" theory that explained the earlier composite-collection bugs) both left the mismatch unchanged — it followed the *value*, not the name or a collection/mode structure.
* **Root cause, confirmed with a precise reproduction**: alpha `0.025` sits exactly on the one boundary where two independently-correct rounding strategies disagree. Push's `a.toFixed(2)` rounds `0.025` up to `"0.03"` (floating-point `0.025` is actually stored fractionally above the exact value). Pull's old path first quantized to a byte — `Math.round(0.025 * 255) = 6` → hex `"06"` — and `token-diff.ts`'s `normaliseColor` then re-derives a float from that hex for comparison: `6 / 255 ≈ 0.0235` → rounds to `"0.02"`. `0.03 ≠ 0.02`, so every pull flagged it as changed, permanently, no matter how many times the repo was re-pushed — while push's own comparison, never touching the byte-quantization step, correctly agreed with what was already committed. Every other alpha value in the palette (5%, 10%, 20%, …) happens to survive the extra byte round-trip without landing on a similar boundary — this was never about "some colors are broken," only about one specific alpha value colliding with a rounding edge two parallel implementations handled differently.
* **Same bug class as the ghost-alias and structural-collision fixes above**: two independently-written re-implementations of "convert a raw Figma value to a comparable string" (`figma-to-tokens.ts` for push/file-writing, `useFigmaValues.ts` for pull) drifting apart in a way neither's own tests could catch, because each was internally self-consistent — the mismatch only exists *between* them. Worth remembering next time a push/pull asymmetry shows up: check whether the two directions actually share a value-conversion function, or only assume they do.
* **Test coverage**: 1 new test in `useFigmaValues.test.ts` reproducing the exact live shape — alpha `0.025` formats as `"rgba(0, 0, 0, 0.03)"` in both `values` and `rawValues`, matching what push already writes. Confirmed via git-stash that it fails with the old `"#00000006"` output without the fix. Full suite (233 tests) passes; `npm run typecheck`/`npm run build` clean.

### First Real Push With JS/TS/Dart/Swift Enabled Found Two Genuine Syntax-Breaking Bugs
* **Decision**: `js.ts`'s `serialize` now quotes an object key unless it's a fully valid bare identifier (`/^[A-Za-z_$][A-Za-z0-9_$]*$/`), not just "doesn't start with a digit." `dart.ts`'s and `swift.ts`'s identical `toDartFieldName`/`toSwiftFieldName` now prefix the whole generated identifier with `_` when it would otherwise start with a digit — a digit *mid*-identifier (`colorBrand500`) is fine in both languages, only a *leading* one is rejected.
* **Found live** (Vy's Spor system, the first real push after enabling JS/TS/Dart/Swift for the first time — CSS had been the only output format exercised against real data until now): two independent, confirmed-compile-breaking bugs, in different generators, from different token shapes:
  1. A Figma variable named with a bracket/comma segment (e.g. a `stroke`/`spacing`/`radius` scale using `[md]`, `[1,5]`-style names) produced a JS/TS object key like `stroke[md]: "2"` — not a computed property, a bare invalid token followed by a colon. Confirmed a genuine syntax error, not a formatting quirk, by actually executing the generated file as an ES module (`node file.mjs`) — `node --check` on the plain `.js` file misleadingly reported no error, but running it for real threw `SyntaxError: Unexpected token '['` at the exact line.
  2. A Figma size step literally named `2xl` (an ordinary type-scale name alongside `xs`/`sm`/`md`/`lg`/`xl`) was the *first* path segment for several tokens, producing a whole identifier starting with a digit (`2xldisplayLetterspacing`) — invalid in both Dart and Swift, which (unlike JS/TS) never allow a leading digit even though one mid-identifier is completely normal (`colorBrand500` is fine).
* **Why `node --check` didn't catch bug 1**: worth remembering for next time — `node --check` on a plain `.js` file containing top-level `export` apparently didn't fully validate the object-literal body the way running the file for real does. Don't trust `--check` alone for this kind of validation again; execute the generated file (as `.mjs`, or with `--input-type=module`) to get a real answer.
* **Same underlying bug class as the alpha-rounding fix above**: `toDartFieldName` and `toSwiftFieldName` are byte-identical duplicate functions across two files — worth extracting to one shared helper next time either needs to change, so a fix to one can't silently miss the other. Not done as part of this fix, to keep the change minimal and scoped to the actual correctness bug.
* **A related, lower-severity risk noticed but not fixed**: both functions' sanitization strips *all* non-alphanumeric characters (`.replace(/[^a-z0-9]/g, "")`), including the comma in a decimal-style segment like `0,5` → `05` — silently identical to whatever a literal segment named `05` would produce. No actual collision found in Spor's real data, but it's a latent name-collision risk worth knowing about if a Dart/Swift field ever looks wrong for a decimal-scale token.
* **Test coverage**: 3 new tests in `transformer.test.ts` reproducing the exact live shapes — a bracket-containing key is quoted in JS/TS output; a leading-digit path segment gets an underscore prefix in both Dart and Swift. Confirmed via git-stash that all 3 fail with the exact live output (`stroke[md]:` unquoted; `static const double 2xlDisplayLetterspacing`) without the fix. Full suite (236 tests) passes; `npm run typecheck`/`npm run build` clean.

### Collection Provenance Tracking — Apply Routes Each Token Back to the Real Collection It Came From
* **Decision**: `Metadata.figma.collectionSources` (new, optional field, sibling to `figma.collections`) records, per role, which real Figma collection each top-level path segment (`black`, `blue`, `primitive`, …) came from — the same granularity `groupByFirstSegment`/`buildPrimitiveFiles` already uses to split a role's tokens into separate files, so no new concept of "segment" had to be invented. `figma-to-tokens.ts`'s new `buildCollectionSources(variables, names)` computes it from live Figma data (every `FigmaVariable` already carries its own `collectionName`); `CollectionMapping.tsx`'s save handler is the only place that writes it, alongside the `figma.collections` mapping it already owns. On apply, `sync-logic.ts`'s new `buildApplyPayloads`/`buildCleanApplyPayloads` use it to fan a single role+mode's tokens out into one `APPLY_TOKENS` message per real target collection, instead of always sending everything to `collections[role][0]` — `Sync.tsx`'s `handleApplyAll`/`handleCleanApplyAll` now send one message per returned payload and size `applyAllRemaining` off the actual payload count, not the diff/collection count.
* **Why this exists**: found live, immediately after fixing the equivalent push-side bug (previous decision) — pulling a role backed by more than one physical Figma collection (a real project: `primitives` role backed by both `size` and `primitives`) put *every* token in the role, including 558 real color values, on track to be created inside whichever collection happened to be listed first. Confirmed via direct inspection of `figma-variables.ts`'s `applyTokensToCollection` that this isn't just organizationally wrong: its exists-or-create check (`collectionVars`) is strictly scoped to the target collection's own variables, so applying into the wrong one creates a **duplicate** variable rather than updating the real one — later alias-by-name resolution (`allVarsByName`, a plain `Map`) becomes ambiguous between the two. The user's own framing: this needs to work for *any* role a design system might have split across collections, not just primitives, since the underlying cause (Figma's one-mode-axis-per-collection limit) applies equally to themes, semantic, and global.
* **Why recorded at "Map collections" save time, not on every push**: the regular Sync push flow never writes `metadata.json` at all today — only `CollectionMapping.tsx` and `OutputFormats.tsx` do, each owning their own slice of config. `collectionSources` fits naturally into the first: it's already the screen that reads live Figma collections and decides `figma.collections`, so recording "which collection each segment currently lives in" at that same moment needs no new plumbing and doesn't touch the push hot path at all. Trade-off, stated plainly: provenance only refreshes when the user re-saves that screen, not on every push — acceptable since that's the same action that already defines the role mapping in the first place.
* **Fallback keeps this fully backward-compatible**: a segment with no entry in `collectionSources` (a `metadata.json` from before this shipped, or a token added by hand since the last save) falls back to `collections[role][0]` — byte-identical to today's single-target behavior. With `collectionSources` absent entirely (the default via `parseMetadata`'s existing spread-over-defaults pattern — no special migration code needed), every project with a single collection per role sees zero behavior change; `buildApplyPayloads`/`buildCleanApplyPayloads` both return exactly one payload in that case, confirmed by tests.
* **Scope, deliberately not covered here**: this only routes *where a token is created/updated* on apply. It does not add deletion-safety provenance for Clean Apply (canonical-model.md §8's other open question, referenced from "Merge-not-replace for Clean Apply" below) — a role-wide Clean Apply still can't tell whether a token that no longer exists in the repo was ever real, only which collection it *would* target if it were being written.

### GitHub File Content Must Decode/Encode Base64 as UTF-8, Not Latin-1
* **Decision**: `useGitHub.ts` now decodes GitHub Contents API payloads via `decodeBase64Utf8` (base64 → raw bytes → `TextDecoder("utf-8")`) and encodes writes via `encodeUtf8Base64` (`TextEncoder` → raw bytes → base64), replacing plain `atob(...)` on read and `btoa(unescape(encodeURIComponent(...)))` on write.
* **What was actually broken**: plain `atob` decodes base64 into a "binary string" — one JS character per *byte*, not per Unicode code point. Any multi-byte UTF-8 character (an em dash, `—`, U+2014, is 3 bytes) came out as three separate mis-decoded Latin-1 characters instead of reassembling into one. The old write-side idiom (`btoa(unescape(encodeURIComponent(str)))`) is the correct pairing *for a correctly-decoded string*, but applied to an already-corrupted one it double-encodes, producing mojibake on GitHub too.
* **Found via a real PR, not inspection**: the Collection Mapping screen's save round-trips an existing `metadata.json` byte-for-byte (reads it, changes only `figma.collections`, writes the rest back untouched) — the first code path in this project to genuinely round-trip a file containing hand-written prose. The actual PR diff showed `"...doesn't match anything — Coop..."` (correct, on the removed line) becoming `"...doesn't match anything â Coop..."` (mojibake, on the added line). The bug was already latent — every prior push wrote fresh JSON built straight from Figma variable data, which happened never to round-trip existing file bytes — this is the first flow that did.
* **Fix verified with a test reproducing the exact corruption** (`useGitHub.test.ts`): encodes a string with an em dash the way GitHub's API actually would, decodes it with the fixed helper, and asserts it comes back byte-for-byte identical — plus a corresponding encode-side test and a plain-ASCII regression check.

### Primitives Is a Genuine Multi-Axis Layer, Not a Single Flat Set of Values
* **Decision**: Primitives can now be genuinely multi-mode — one `ResolvedCollection` per size mode, mirroring exactly how Themes already emits one collection per named theme. Fed by the `sizes` role (`figma.collections.sizes`) as a real second axis, with mode order and breakpoints configured via new `Metadata.sizes: string[]` (base mode first) and `Metadata.sizeBreakpoints: Record<string, number>` — mirrors `themes`/`colorSchemes` exactly. Zero behavior change for any repo with no Size axis configured: `sizes: []` collapses every code path back to today's single "Value"-mode primitives.
* **Rationale — this replaces a real, confirmed bug, not a hypothetical.** Before this, `primitives`/`global` were architecturally forced single-mode. The stress test's own workaround — mapping Coop's real two-mode `Size` collection into the `primitives` role via the mapping UI — produced **silently inconsistent output**: `figmaToTokenFiles` (writes the committed JSON) used only the collection's first mode, while `figmaToCollections` (feeds the CSS generator) merged every mode in array order, last one winning. Concrete proof from a real PR: `primitive.json` had `font-size.1: 11px`, `dist/tokens.css` had `--primitive-font-size-1: 12px` — same token, two different values, no error or warning anywhere. A silently wrong value is worse than a missing one.
* **File layout**: new `primitives/sizes/{mode}.json` (e.g. `mobile.json`, `desktop.json`) — mirrors `semantic/themes/{name}.json` exactly, one level nested under `primitives/` instead of `semantic/`. Existing flat `primitives/{segment}.json` files are completely untouched; a repo with no Size axis never has this directory at all.
* **Both sync directions**:
  * `token-merger.ts` (GitHub → Figma): `buildLayers` gains a `sizes` bucket populated from `primitives/sizes/{mode}.json`; `parseRepository` emits one primitives collection per mode (shared/invariant primitives deep-merged with that mode's own values) when `layers.sizes` is non-empty, else today's single "Value" mode.
  * `figma-to-tokens.ts` (Figma → GitHub): `figmaToCollections`/`figmaToTokenFiles` both changed signature to take the full `Metadata` (not just `CollectionNames`) — needed for `metadata.sizes`' mode-order to determine which mode is the *default* deterministically, rather than guessing from whatever order Figma happens to return `collection.modes` in (fragile: reordering modes in the Figma UI would silently flip which one is "base" with no PR to review). `figmaToTokenFiles` gained the same per-mode-file-merge treatment (`mergeIntoModeEntries`) themes/semantic already had, since two collections contributing the same size-mode name need to merge into one file, not overwrite.
* **CSS generation** (`css.ts`) reuses the exact mechanism already built and tested for light/dark, generalized: `primitivesCols` is now a list, not a single `.find()`. The config-determined default mode's values go straight into `:root`; every other mode gets a `diffTokens` override under `[data-size="desktop"]` (explicit pin) **and** — when `sizeBreakpoints` configures one — an *unconditional* `@media (min-width: …)` wrapping `:root` directly. This deliberately differs from color-scheme's `[data-color-scheme="auto"]` wrapper: a breakpoint is something a page is always crossing, not an opt-in preference, so no wrapper attribute is needed to get the responsive behavior at all — `[data-size="…"]` is purely the override/pin on top.
* **A second real bug found and fixed while building this, previously latent**: `splitSharedSemanticTokens` (the light/dark dedup mechanism from the earlier CSS dedup decision) hoisted the *original resolved-literal* `TokenValue` into `:root` when a semantic token was identical across schemes, discarding whatever `var(--*)` reference the equality check itself had just computed. Harmless as long as nothing exercised "identical across schemes AND aliases a real, referenceable target" — which never happened before a typography-style token referencing a size-varying primitive did exactly that in this work's own tests. A semantic token hoisted to `:root` now keeps its live `var(--*)` reference instead of silently baking in a static snapshot — the whole point of the var() cascade in the first place. Fixed by having `splitSharedSemanticTokens` return the already-computed final CSS value string, not the pre-computation token; `cssBlockWithExtra` appends it directly instead of re-running it through `formatCSSValue`.
* **Test coverage**: real multi-mode-merge and default-mode-selection tests added in `token-merger.test.ts`, `figma-to-tokens.test.ts`, and `css.test.ts` (10 new tests total, including one reproducing the exact `formatCSSValue`-double-application bug above).
* **Breakpoints are optional, deliberately — this is not Coop-specific.** `[data-size="…"]` is the correct, complete mechanism for any number of modes with zero config: how `data-size` gets set on a real page (an app's own media query, a container query, JS, server-side device detection) is an application concern Token Spark has no business deciding. `@media (min-width)` is a pure convenience layered on top for teams that want automatic viewport switching without wiring that up themselves — left blank, nothing breaks. Checked against how other systems handle this before committing to the shape: Material Design varies tokens by window-size class but leaves which class is active to app layout logic, not the token layer; Tailwind's breakpoint scale is project-configurable, not asserted by the framework; most component libraries (Spectrum, Fluent, Lightning) push "when" to container queries or component props. Pushing the breakpoint decision out to the consumer, same as those, is the right shape — Token Spark isn't in the business of knowing a project's canonical breakpoints.
* **Found and fixed from asking "what if there are 4 size modes?"**: `min-width` media queries aren't mutually exclusive — a 1500px viewport matches every `min-width: 600px`, `min-width: 1024px`, etc. query simultaneously. The first version of this diffed every non-default mode against the *base* mode only; a property that changes at tier 2 then reverts at tier 3 (back to the base value) would show no override in tier 3's block (looks identical to base) and stay silently stuck at tier 2's value once both queries match at a wide viewport. Invisible with exactly one non-default mode (Coop's actual mobile/desktop case — nothing to stack), real from three tiers on. Fixed by sorting responsive tiers ascending by breakpoint and diffing each one against the tier immediately below it, not always the base — the same "small, then medium, then large" source-order rule Coop's own build tool encodes for exactly this reason. `[data-size="…"]` explicit pins are unaffected — they always diff against base, correctly, since setting the attribute is a complete override independent of any media query.

### Default Theme Selection Finished Everywhere It Was Missed
* **Decision**: `css.ts`'s `defaultTheme` and `figma-to-tokens.ts`'s `defaultThemeRaw` now both pick the default theme via `metadata.themes[0]` (case-insensitive), mirroring the exact pattern `defaultPrimitives`/`defaultSizeModeRaw` already used for the Size axis in the same two files. `Sync.tsx`'s pull/push diff joins (matching a Figma mode against a GitHub `capitalise()`-derived mode name) are now case-insensitive too.
* **Found by running the new project-scoped `/code-review` skill** against the plugin's core logic and Figma integration, then verifying each claim against the actual code before acting — three real findings out of seven, all the same underlying issue: `css.ts` and `figma-to-tokens.ts` picked the default theme by array/Map order (`themeCols[0]`, `themeModes.values().next()`) instead of `metadata.themes[0]`, the exact bug already found and fixed for `token-merger.ts` and for the Size axis earlier — just never finished in these two spots. All three test suites' own fixtures happened to name their default theme `"Default"`/`"default"`, matching `defaultMetadata()`'s placeholder — the same masking effect already documented for the `token-merger.ts` fix. New tests deliberately use a realistic theme name (`"original"`/`"christmas"`) with the collections array in the opposite order from `metadata.themes`, which is what actually exercises the bug.
* **Other four findings from the same review — three fixed next (see the following decision), one still deliberately deferred**: `resolveInlineRefs` picking an arbitrary mode for an embedded `{ref}` inside a composite string value (e.g. a shadow token) touches the explicitly-not-yet-audited shadow/gradient/border DTCG coverage question (`canonical-model.md` §8) and wasn't acted on for that reason — the other three (apply-flow error accounting, the Text Style unit round-trip, and `createTokenPR`'s sequential writes) are fixed.

### Three More Findings From the Same `/code-review` Pass, Fixed
* **Apply-flow error accounting**: `main.ts`'s `drainApplyQueue` reports a task that throws before returning as a plain `ERROR` message, not `TOKENS_APPLIED`/`TEXT_STYLES_APPLIED` — which `Sync.tsx`'s batch-apply counter (`applyAllRemaining`) never decremented for, so a mid-batch failure meant the collections that *did* succeed never got a final summary shown, and the queue kept draining in the background with no visible effect. Fixed by making the `ERROR` handler batch-aware the same way `TOKENS_APPLIED`/`TEXT_STYLES_APPLIED` already are: it now decrements `applyAllRemaining` and accumulates into a new `applyAllBatchErrors` ref, finalizing (via a new shared `finishApplyBatch` helper) only once every task in the batch has reported back one way or the other.
* **Text Style `letterSpacing`/`lineHeight` PIXELS-vs-PERCENT round-trip**: reading a Text Style discarded which unit Figma actually stored, and applying one always wrote back `PERCENT` — a Text Style with pixel-based letter spacing (2px) would silently become a percentage (2%, i.e. ~0.32px of a 16px font) on any pull-then-push round trip. Fixed by encoding the unit as a string suffix instead of discarding it: a bare number ("150") still means PERCENT — this repo's own existing convention, confirmed directly in `tokens/primitives/typography.json` ("150" = 150%) — while an explicit "px" suffix ("16px") now means PIXELS and round-trips correctly. Every existing PERCENT-based token is completely unaffected. The two pure helpers (`formatUnitValue`/`unitFromLiteral`) moved from `figma-text-styles.ts` (untestable without a Figma sandbox mock) into the already-tested `shared/text-style-figma-fields.ts`, with new tests proving the exact round trip.
* **`applyTypographyStyles` counted a style as applied even when one of its fields errored** — unlike `figma-variables.ts`'s `applyTokensToCollection`, where `count` only increments on a per-value confirmed success. Fixed by comparing the shared `errors` array's length before and after each style, only incrementing `count` when nothing new was pushed.
* **`createTokenPR` wrote one commit per file, sequentially** — not just slow (O(N) round trips), but unsafe to naively parallelize, since each Contents-API PUT commits against the current branch head and concurrent PUTs would race that head (409 conflicts). Rewritten to use the Git Data API properly instead of working around the Contents API's limitation: create all file blobs in parallel (a blob is a pure content-addressed object, no branch/ref state involved, genuinely safe to parallelize), then one tree (`base_tree` carries over every untouched file), one commit, and one branch ref pointing straight at it. Net effect: one clean commit per PR instead of N noisy ones, no per-file existing-sha GET needed at all (the old Contents-API approach's own conflict-avoidance step, no longer necessary), and PR-creation latency no longer scales linearly with file count. New test asserts exactly one blob call per file and exactly one tree/commit/ref call regardless of file count, plus the correct `base_tree`/`parents` wiring.

### `Sync.tsx`'s Core Diff/PR Logic Extracted Into a Tested Module
* **Decision**: the pure, non-React parts of `Sync.tsx` — matching a Figma collection/mode against a GitHub one, filtering ignored collections, and building the file list for a push PR — moved into a new `shared/sync-logic.ts` (`isIgnoredCollection`, `computePullDiff`, `computePushDiff`, `buildFilesFromDiffs`). `Sync.tsx` now calls these instead of computing inline; the React-specific parts (state, refs, message handling, the apply-batch counter) stay in the component.
* **Rationale**: `Sync.tsx` has had zero test coverage since this project started, despite being where several of this session's real bugs lived — the case-sensitive mode-name join and the apply-flow counter desync both trace back to logic that used to live directly in this file. There's no React component-testing setup in this repo (no jsdom/RTL, no `figma.*`/`fetch` mocks for a mounted component), and building one just to cover this would be a bigger, riskier undertaking than the value at stake. Extracting the part that's actually pure — data in, `CollectionDiff[]`/file list out, no `setState` or refs — makes it directly testable with the exact same lightweight `vitest` approach every other `shared/` module already uses, without touching the React layer at all.
* **What's still not covered, deliberately**: the component-level orchestration (the apply-batch counter/error accumulation fixed earlier this session, clientStorage persistence, branch switching, message-handler wiring) stays in `Sync.tsx` itself and stays untested — genuinely React-and-`figma.*`-coupled in a way that would need real component-testing infrastructure, not just a refactor, to cover. Scoped out on purpose rather than half-built.
* **Test coverage**: `sync-logic.test.ts`, 13 new tests — including one reproducing the exact case-sensitivity bug found via `/code-review` (a lowercase real Figma mode name against a `capitalise()`'d GitHub one), and one confirming platform transformers run against the *full* collection set even when only some collections are selected for the PR itself.
* **Follow-up `/code-review` pass on this same extraction, both fixed**: `Sync.tsx`'s `handleCreatePR` had a `raw && parsed ? ... : []` guard around a state that can't actually occur — `handleCreatePR` is only reachable from the `push-diff` view, which only exists once both refs are set together, and the only code that clears one of them (`onBack`) simultaneously unmounts that view. Replaced the silent `[]` fallback with an explicit throw, since silently building a zero-file PR would be a worse failure mode than a loud one if this invariant ever broke. Separately, `computePushDiff` wrapped its one return value in `{ diffs }` for no reason (unlike `computePullDiff`, which genuinely returns two values) — now returns `CollectionDiff[]` directly.

### Map Collections Derives `themes`/`colorSchemes` From Real Figma Modes, Not Just `figma.collections`
* **Decision**: `CollectionMapping.tsx`'s save now also derives and writes `metadata.themes` and `metadata.colorSchemes` from the real Figma mode names of whatever's currently assigned the `themes`/`semantic` roles — the same pattern already built for `sizes`. Names are sanitized (lowercase, spaces/slashes → hyphens) to match exactly what `figma-to-tokens.ts`'s `sanitizeFileName` uses when writing the corresponding files, since that's the string `parseRepository` looks them up by. An empty derivation (nothing currently assigned that role) falls back to whatever was already there rather than blanking it — Figma is only the source of truth for these *when something is actually mapped*.
* **Rationale — a real, previously-invisible bug, found while assessing first-run readiness.** `defaultMetadata()` ships `themes: ["default"]`, `colorSchemes: ["light", "dark"]`. `parseRepository` looks up the default theme via `layers.themes[metadata.themes[0]]` and each color scheme via `layers.semantic[scheme]` — exact-string lookups against real file names. A real theme is essentially never actually going to be named "default" — so on every first project, before this fix, `defaultThemeTree` silently resolved to an empty object, and cross-reference resolution for `{light.*}`/`{dark.*}` aliases against "the default theme" silently failed. This stayed invisible because this project's own test fixtures happened to name their default theme file `default.json`, coincidentally matching the placeholder — the bug only shows up with a realistic name, which is exactly the case new tests were written against (`token-merger.test.ts`, "theme/colorScheme lookup is case-insensitive").
* **Defense in depth**: `token-merger.ts`'s theme/colorScheme/size-mode lookups are now case-insensitive (`findCaseInsensitive`), not just exact-string. `metadata.json` is explicitly meant to be hand-editable (`docs/principles/no-lock-in.md`), and a casing slip between a hand-edited config and a real file name is exactly the kind of thing that should degrade gracefully, not silently drop data.

### Transformer Output Shape Stays Opt-In/Opt-Out Only, Not Configurable
* **Decision**: the CSS/JS/Dart/Swift transformers' output shape (selector strategy, variable naming, file layout) stays fixed and opinionated — not made configurable. What *is* now real: `Metadata.platforms`/`PlatformConfig` moved from an untyped `as MetadataWithPlatforms` cast local to `transformer/index.ts` into the actual `Metadata` interface in `token-merger.ts`, and a new **Output formats** screen (`OutputFormats.tsx`, same "read metadata.json → edit → PR" pattern as Map Collections) lets a team choose which of CSS/JS/TS/Dart/Swift generate on push, instead of hand-editing `platforms.*.enabled`.
* **Rationale, researched against real prior art before deciding, not assumed**: checked directly against Style Dictionary's own docs (the most flexible, most widely-adopted tool in this space, and literally what Coop's own extractor is built on) — even *its* built-in `css/variables` format hardcodes `:root`; getting a class-based multi-theme selector scheme (what Coop needed) requires writing a real custom format function against Style Dictionary's plugin API, not a config option. Coop's `web-design-extractor` *is* that custom code. Nobody in this ecosystem ships arbitrary output-shape configuration as JSON knobs, because the actual space of things a team might want is open-ended enough that the config surface becomes its own small programming language — exactly the kind of premature, speculative abstraction this project's own engineering principles argue against, and worse for a brand-new design system specifically (no existing convention to match, so it's pure decision fatigue for no payoff).
* **What closes the gap instead**: Token Spark's canonical model is already DTCG (`canonical-model.md` §2) — checked directly against the DTCG 2025.10 spec, `color`/`dimension`/`fontFamily`/`fontWeight`/`number` all match its seven official base types exactly (two minor, pre-existing, non-blocking gaps found in the same check: `boolean`/`string`, used for Figma `BOOLEAN`/`STRING` variables, aren't official DTCG types). Style Dictionary v4 has genuine native DTCG support. That means Token Spark's raw `tokens/**/*.json` is, in principle, already valid input to a team's *own* Style Dictionary (or similar) pipeline, no adapter needed — a team with existing infrastructure doesn't need Token Spark's transformers to match their conventions, it needs to point its own tool at `tokens/` and leave every `platforms.*` off. Documented as a first-class path in the README ("Already have a build step?"), not something to reverse-engineer from `metadata.json`'s shape.
* **Full reasoning**: [docs/design/transformer-configurability.md](docs/design/transformer-configurability.md).

### Developer-First Toolchain: Core Extraction + CLI + CI (direction, not yet built)
* **Decision**: Extract everything in `plugin/src/shared/` (token-merger, token-format, token-diff, all transformers — pure TypeScript, zero Figma API dependencies) into a `@tokenspark/core` package consumed by both the plugin and a new CLI (`tokenspark build | validate | diff | watch`). Platform outputs (CSS/JS/TS/Dart/Swift) move out of plugin-created PRs entirely: a GitHub Action runs `tokenspark build` on merge and publishes the artifacts (npm package or release branch). The plugin shrinks to the Figma-side boundary only — designers pull/push variables; developers never need Figma or the plugin.
* **Rationale**: The Figma Variables REST API is Enterprise-gated and plugins cannot run headless, so terminal-driven Figma sync is impossible on standard plans. But developers only need the token repo, which is already the source of truth. Moving compilation to CLI/CI also means PRs contain only token JSON (smaller diffs, no generated-file conflicts) and structurally prevents broken artifacts from being committed (a `dist/{colorScheme}.js` containing TypeScript syntax once shipped via a plugin PR).
* **Considered and rejected — localhost relay bridge**: a plugin window polling a local server so a CLI could drive it. Rejected: Figma must still be open with the plugin running, local-network `networkAccess` rules are fragile across desktop/browser, and it simulates headless without being headless. The core extraction removes the need.
* **Future provider — Enterprise REST**: shape `@tokenspark/core` around a provider interface so an Enterprise-plan REST provider can later offer true headless two-way sync (`tokenspark pull --from-figma`, scheduled CI backups of Figma state). Not built until there is demand; verify current Figma plan gating at that time.
* **Accepted limitation**: on non-Enterprise plans, Figma → GitHub always requires a designer to click Push in the plugin. Best mitigation: keep push one-click, and optionally a Figma file-update webhook that nudges designers to sync (webhook availability is plan-dependent — verify).

### Token Studio Off-Ramp: Canonical Model + Adapter Architecture (direction decided, mechanics under analysis)
* **Decision**: Learn from Token Studio's format — the three-layer model, the global/brand split, composite typography — without inheriting its shape. Token Spark's core will own a neutral canonical model (DTCG-based, with `$extensions` for the properties DTCG doesn't cover), and Token Studio becomes **one adapter** that translates into it, not something the core is built around. No adapter's concepts (`$themes.json`, `enabled`/`source`, `group` dimensions) may leak past the adapter boundary into diff, resolution, or transformers. Full reasoning, the axis model, the Figma API findings, and the open questions are in `docs/design/canonical-model.md` — treat that document, not this entry, as the source of truth for mechanics.
* **Rationale**: A reader built directly around Token Studio's concepts just relocates the lock-in. Building against the open DTCG standard instead means a Token Spark repo stays readable by any DTCG-aware tool with zero adapter — the literal opposite of `$themes.json`'s unreadability — while still letting Token Studio repos convert in.
* **Migrate-once, not interoperate-forever**: the importer is a one-time reader; after conversion the repo is a native Token Spark repo and none of Token Studio's plugin-cache/drift failure modes (`docs/interop/token-studio.md`) have anywhere to live. Continuous bidirectional sync against `$themes.json` is explicitly not the design center; a thin evaluation bridge is a possible future add-on only if real demand appears.
* **Axes are not peers**: composing axes (brand, colour-mode — together select the resolved value, realistically ≤3) are a different kind from modifier axes (size, density — each declares which token categories it affects, layered on top, never touching what composing axes touch). This replaces an earlier "N independent axes" framing that didn't match observed reality.
* **Composite tokens surfaced two concrete, previously-unscoped gaps**: (1) DTCG's `typography` type has 5 properties, Token Studio's has 9 — the 4 extras need `$extensions`, and `shadow`/`gradient`/`border` need the same audit (open, see canonical-model.md §6/§8); (2) Figma has no composite variable type at all — composite typography/shadow tokens need Figma **Text Styles** / **Effect Styles** support, a Plugin API surface Token Spark doesn't touch yet. "Figma Styles export" moves from Not Planned to Planned (see §4 below and the README status table).
* **Default is faithful conversion, not improvement**: the importer transcribes structure as-is; any "here's how this could be better organised" analysis is a separate, optional, non-blocking report — most teams migrating in want it to work, not to be restructured.
* **Token Studio exporter** (round-trip out) is committed as a direction for later — the strongest concrete proof of no-lock-in — but not scoped or timed yet.
* **Not yet resolved** — see `docs/design/canonical-model.md` §8: shadow/gradient/border DTCG coverage; how composing axes map onto Figma's 40-mode-per-collection ceiling; the actual mechanics of provenance tagging for merge-not-replace; exporter scope and timing. Do not start implementing the adapter architecture from this entry alone.

## 2. Code Invariants (read before editing)

Non-obvious constraints that must hold; each was the source of a real bug.

* **Sync flows must not read metadata from React state.** The `usePluginMessage` handler in `Sync.tsx` is registered once with a frozen closure; collection names and `ignoredCollections` must be read from the parsed repository held in refs (`pendingGitHub` / `pendingParsed`), never from component state.
* **Swift hex ordering**: token hex is CSS-ordered (`#RRGGBBAA`), but the generated `Color(hex:)` helper parses 8-digit hex as `AARRGGBB`. The transformer must move the alpha byte to the front. The Dart transformer does the equivalent (`Color(0xAARRGGBB)`).
* **Output-path templates must always be substituted.** No `{colorScheme}` (or future placeholder) may survive into a written file path — a literal `dist/{colorScheme}.js` was once committed to GitHub. There is a test asserting this for Dart; extend it for any new placeholder.
* **Default output paths resolve sibling to the tokens folder** (`resolvePath` receives the *raw* `cfg.output`, which may be undefined — never a pre-defaulted value, or the sibling fallback silently stops applying).
* **Figma mode names must be sanitised before becoming file names** (`sanitizeFileName`: lowercase, spaces/slashes → `-`). The parser (`buildLayers`) only reads `primitives/*`, `semantic/global/*`, `semantic/themes/*`, and `semantic/{scheme}.json` — a path outside that shape is silently dropped on the next pull.
* **`parseMetadata` must return fresh objects** (via `defaultMetadata()`), never a shared singleton — callers may mutate nested objects.
* **The mode-removal loop in `figma-variables.ts` iterates a snapshot** (`[...collection.modes]`) because `removeMode` mutates the live array; the lint suppression there is intentional.
* **`npm run typecheck` must check the real per-project configs, never the root `tsconfig.json`.** The root config is a solution file (`files: []`, only `references`) — `tsc`/`tsgo --noEmit` against it with no `--build` flag silently checks nothing and exits 0. Found in July 2026 after it had apparently been a no-op for an unknown period: real type errors (a missing import, a broken `tsconfig.plugin.json` option, a type-modeling gap in `TokenTree`) were sitting in the codebase undetected. The script now runs `-p tsconfig.app.json` and `-p tsconfig.plugin.json` explicitly (see `package.json`'s `typecheck:app`/`typecheck:plugin`). **Do not "simplify" this back to a bare `tsc --noEmit`/`tsgo --noEmit`** — it will silently stop checking anything again.
  * **This recurred in September 2026, not in the script this time but in how it was invoked.** An assistant session ran ad-hoc `npx tsc --noEmit` directly (bypassing `npm run typecheck` entirely) across four consecutive PRs (#9–#12) and reported "typecheck clean" each time — every one of those claims was actually checking nothing, the exact failure mode this bullet already named. It masked a real, pre-existing type error (see the `bucket()` invariant below) that had been silently broken since PR #8, three PRs earlier. Found only when a fifth PR's own new code needed closer attention and `npm run typecheck` was finally run directly. **Lesson for any agent working in this repo: always run the actual `npm run typecheck` (or `npm run build`, which exercises the same compiler) — never assemble your own `tsc`/`tsgo` invocation, no matter how reasonable it looks.**
* **`bucket()`'s generic type parameter must be pinned explicitly at the call site, not left to infer from an object-literal `make` callback.** `sync-logic.ts`'s `buildApplyPayloads`/`buildCleanApplyPayloads` both call `bucket(map, key, () => ({ tokens: {}, ... }))` — TypeScript's inference from the *callback's* return type can silently win over the `Map`'s own explicit type argument, collapsing the inferred type to the empty-literal shape (`{}`) and making every downstream property access (`group.tokens[path] = ...`) implicitly `any` with no reported error at the call site itself — the error surfaces one level down, at the indexed assignment. Introduced with the Primitives+Sizes composite fix (PR #8) and undetected for three subsequent PRs due to the invariant above. Fixed by annotating each field in the `make` callback's return literal (`{} as Record<string, TokenValue>`, etc.) so the callback's own inferred return type already matches `T`, instead of relying on cross-argument unification.
* **`tsconfig.app.json` must not include `src/plugin`.** That directory needs Figma's ambient sandbox types (`@figma/plugin-typings`, only in `tsconfig.plugin.json`'s `types`); including it under the app config produces a wall of false `Cannot find name 'figma'` errors that look real but aren't. `tsconfig.app.json` is scoped to `["src/ui", "src/shared"]` for this reason.
* **`TokenTree`'s index signature includes a bare `string` arm** (`TokenValue | TokenTree | string`) to legally model `$`-prefixed metadata (`$description`, and the group-level `$type: "typography"` marker) coexisting with nested children in the same object — this is real, valid data this codebase already produces and reads. Any code walking a `TokenTree` must explicitly skip `$`-prefixed keys before assuming a value is `TokenValue | TokenTree` (existing code already does via `key.startsWith("$")`); don't assume the value at any key is object-shaped without checking.
* **A `ResolvedCollection.modeName` produced on the push side must be Figma's real mode name, never fabricated.** `buildFilesFromDiffs` (`Sync.tsx`) matches the *original* Figma collection data against the diff/selection UI's keys by `${collectionName}/${modeName}` — a made-up mode name (e.g. a hardcoded `"Value"`) breaks that match silently. The collection still shows as selected in the UI; it just never makes it into the generated PR. Found from a real Coop push where `primitives` displayed as selected but its file never appeared. If a future change needs to represent multiple Figma modes as one logical entity (merging primitives/global across several physical collections, say), the reported `modeName` must still be a name that actually exists in the raw Figma data being filtered against — never invented.

### Map Collections: Structural Validation Checklist (design accepted, not yet built)

Requested directly by the user (September 2026) while testing a second, structurally
different design system (Vy's Spor) against Token Spark for the first time — a
project could reach a broken or confusing state entirely through *correct use of
the mapping UI*, with no signal anything was wrong until a later push/pull/generated
file surfaced it indirectly. Every item below traces to a real incident, most from
this session — not a speculative "what could go wrong" list. Scope deliberately
narrow: warn on confirmed failure shapes, not a general-purpose linter.

1. **A `primitives`-role collection with more than one Figma mode while
   `figma.collections.sizes` is empty.** Found live on the Spor test (PR #1 → #2):
   size-varying data (font sizing) was folded into the `foundation` primitives
   collection as extra modes instead of getting its own `sizes`-role collection —
   the exact shape the Size axis feature (§1 *Primitives Is a Genuine
   Multi-Axis Layer…*) was built to replace, and the earlier Coop stress test hit
   the identical mistake before that feature existed. Warn: "this collection has
   N modes but no `sizes` role is mapped — did you mean to split size-varying
   fields into their own collection?"
2. **The same physical Figma collection assigned to more than one role.**
   Already detected — `token-merger.ts`'s `parseMetadata` emits a `console.warn`
   (§1 *Multiple Figma Collections Per Role…*) — but a non-developer user never
   opens devtools, so today this is silent in practice. Surface the same check as
   a visible warning in Map Collections' own UI, not just the console.
3. **A `themes`-role collection whose own top-level token groups are named like
   color schemes** (`light`/`dark`, case-insensitive) **while a genuine
   `colorSchemes` axis already exists elsewhere (Semantic).** Found live on the
   Spor test: the `theme` collection's real Figma modes are the three brands
   (`vy`/`it`/`cargonet`), but its variables are also grouped under literal
   top-level `Light`/`Dark` segments — meaning those fields will only ever emit
   as flat, static per-brand values (`--theme-vy-Light-*`), never gaining the
   `[data-color-scheme]` `var(--*)` cascade Semantic tokens get. May be exactly
   what Spor intends; may be a mapping mistake — either way the mapping screen
   currently gives no signal either way. Warn, don't block.
4. **No visible confirmation of which theme/size/scheme is "the default."**
   `metadata.themes[0]`/`sizes[0]`/`colorSchemes[0]` silently becomes `:root` in
   every generated output (§1 *Default Theme Selection Finished…* and its
   sibling fixes) — correct today, but invisible in the UI: nothing on the
   mapping screen tells the user which entry that array order actually picked
   before they push. Surface it explicitly ("Default theme: vy — this is what
   `:root` uses") rather than requiring a read of the generated CSS to find out.
5. **A FLOAT Figma variable whose name matches none of `inferType`'s
   dimension-detecting keywords** (`dimension|size|spacing|padding|radius|width|
   height|border|gap`). Found live on Coop (§1 *FLOAT Variables Named
   "dimension"…*) — a real, shipped naming convention silently produced a
   unitless `number` instead of `dimension`, losing the CSS `px` suffix. The
   keyword list is inherently a guess at naming conventions this project hasn't
   seen yet; flag an unmatched FLOAT variable for confirmation rather than
   silently picking `number`.
6. **`figma.collections.global` is `[]`.** Not a mistake — the expected, correct
   shape for any Token-Studio-style migration where typography lives only in
   Text Styles (§1 *Every Transformer Silently Dropped Typography…*; Priority 4's
   now-fixed transformer gap) — but currently silent either way. A reassuring
   info note ("Typography will be read entirely from Figma Text Styles — expected
   if this system has no dedicated Global/Typography variable collection") would
   save a new user from wondering whether something's missing.

**Deliberately left out of this first pass**: content-based heuristics with no
confirmed failure case yet (e.g. "does a `sizes`-mapped collection actually
contain dimension/number fields?") — matches the project's own stance against
speculative validation surfaces (see *Transformer Output Shape Stays
Opt-In/Opt-Out Only*). Add a check here only once it traces to a real incident,
the same bar every item above already meets.

### A General "Advisor" Surface — Recommendations, Not Just Errors and Successes (direction, not scoped)
User's own framing (September 2026): the UI already has a place for "this
succeeded" and "this failed" — there isn't one yet for "this worked, but here's
something worth reconsidering." Proposed as a third message class alongside
the existing success/error `StatusBanner` states, surfaced at the natural point
a user would want it (Map Collections, the push diff, wherever), not as a
separate report screen nobody opens.

Two concrete cases already identified that this would cover, neither built yet:
- **Map Collections' own structural checklist above** — every one of its 6
  items is naturally an advisory ("this looks off, want to fix it?"), not a
  hard error; this direction is the general mechanism that checklist's items
  would actually render through, once built.
- **Typography fields that are literals but shadow a real primitive's
  value** — discussed directly with the user: a raw, unbound Text Style field
  (`fontSize: "24px"`, say) permanently opts out of the `[data-theme]`/
  `[data-size]` `var()` cascade, since there's nothing to override. Auto-binding
  it was explicitly rejected (naming/grouping/collection is a design decision,
  not a sync decision — see the Token Studio adapter's "faithful conversion,
  not improvement" stance) — but *telling* the user "this value matches
  `primitive.font-size.11` — bind it in Figma for live switching?" costs
  nothing and leaves the actual action, and its details, to them.

**Not scoped**: where recommendations get computed (a pass in `figma-to-tokens.ts`?
`sync-logic.ts`?), how many can co-exist without turning into a wall of
suggestions, whether they're dismissable/rememberable per-project. Deliberately
left open until there's a second and third real case beyond the two above to
design the mechanism against — same reasoning as not building the Map
Collections checklist mechanism from one incident alone.
