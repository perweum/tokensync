# Token Format Specification — tokensync/v1

## Overview

This document defines the canonical token format used by the Token Sync plugin. It is the source of truth for all token structure decisions.

The format is inspired by the [W3C Design Token Community Group (DTCG)](https://www.w3.org/community/design-tokens/) draft specification, extended with explicit multi-brand and multi-theme support.

---

## File Structure

```
tokens/
  primitives/
    color.json          Raw colour ramps (12 steps per palette)
    geometry.json       Spacing scale, border radius, border width
    typography.json     Font families, sizes, weights, line heights
    motion.json         Durations, easing curves (optional)

  semantic/
    global/             Theme-invariant semantic aliases
      typography.json   Heading, body, label, code composites
      spacing.json      Component spacing, layout spacing, radius aliases
    brand/              Brand palette mappings — one file per brand
      default.json      brand.N → color.X.N aliases (default brand)
      green.json        brand.N → color.green.N aliases
      {name}.json       Additional brands
    light.json          Semantic colour roles — light theme, uses {brand.N} refs
    dark.json           Semantic colour roles — dark theme, uses {brand.N} refs
    {occasion}/         Optional composition overlays (sparse overrides)
      christmas.json

  metadata.json         Project config: brands, compositions, Figma mapping, platform output
```

### Rules

1. **Primitives are raw values only.** No references to other tokens. No semantic meaning.
2. **Global semantics are theme-invariant.** If a token value changes between light and dark, it does not belong in `global/`.
3. **Brand files map `brand.N` to a specific colour ramp.** `brand.600` in the default brand might be `{color.blue.600}`; in the green brand it would be `{color.green.600}`.
4. **Semantic files reference `{brand.N}` not specific palette steps.** This is what makes brand switching work at runtime without re-generating CSS.
5. **Composition overlays are sparse.** An overlay file only needs to contain tokens that differ from the base theme it stacks on top of.
6. **Component code references semantic tokens only.** Never reference primitives directly in UI code.

## Token Syntax

All tokens follow the W3C DTCG format:

```json
{
  "tokenName": {
    "$type": "color",
    "$value": "#0062ba",
    "$description": "Optional human-readable description"
  }
}
```

`$type` can be set on a group and inherited by all children:

```json
{
  "surface": {
    "$type": "color",
    "default":  { "$value": "#ffffff" },
    "disabled": { "$value": "#f0f0f0" }
  }
}
```

### Supported types

| Type | Example value | Used in |
|---|---|---|
| `color` | `"#0062ba"`, `"rgba(0,0,0,0.1)"` | All colour tokens |
| `dimension` | `"16px"`, `"1rem"` | Spacing, radius, font-size |
| `fontFamily` | `"Inter, sans-serif"` | Typography |
| `fontWeight` | `"600"` | Typography |
| `number` | `"1.5"` | Line height, opacity |
| `shadow` | `"0 2px 4px {color.black.10}"` | Elevation |

## Reference Syntax

References use W3C DTCG curly-brace syntax:

```
{token.path.here}
```

All token files are merged into one flat namespace at resolution time. The path follows the JSON key hierarchy, ignoring file or folder location.

### Examples

```json
"$value": "{color.blue.600}"
```
→ resolves via `primitives/color.json` → `color` → `blue` → `600`

```json
"$value": "{brand.600}"
```
→ resolves via `semantic/brand/default.json` (or whichever brand is active) → `brand` → `600`

```json
"$value": "{geometry.size.4}"
```
→ resolves via `primitives/geometry.json` → `geometry` → `size` → `4` → `"16px"`

### Circular references

Circular references are not permitted and will fail validation.

## Colour Primitive Model

Colour ramps use a 12-step scale. Steps are named by perceptual lightness position:

| Step | Perceptual role |
|---|---|
| `25`  | Lightest background tint |
| `50`  | Light background tint |
| `100` | Surface tint |
| `200` | Subtle border, surface active |
| `300` | Border, surface hover |
| `400` | Muted interactive |
| `500` | Mid-point (equal perceived darkness across all palettes) |
| `600` | Primary interactive default |
| `700` | Primary interactive hover |
| `800` | Primary interactive active |
| `900` | Deep background (dark mode) |
| `950` | Deepest background (dark mode) |

**Key property:** `green.500` and `blue.500` have the same perceived darkness. This is guaranteed by the OKLCH generation in Themebuilder. It makes the system predictable: you can reason about contrast ratios by step number alone.

Ramps are generated by Themebuilder from a single seed colour using OKLCH colour space with fixed per-step luminance targets. The source of truth is always the seed — ramps are never manually edited.

## Brand Palette Model

The Brand collection introduces a `brand.N` indirection layer between semantic tokens and colour primitives.

### Brand files (`semantic/brand/{name}.json`)

Each brand file maps `brand.N` to a specific colour ramp step:

```json
{
  "brand": {
    "$type": "color",
    "25":  { "$value": "{color.blue.25}" },
    "50":  { "$value": "{color.blue.50}" },
    "100": { "$value": "{color.blue.100}" },
    "600": { "$value": "{color.blue.600}" },
    "700": { "$value": "{color.blue.700}" },
    "950": { "$value": "{color.blue.950}" }
  }
}
```

The green brand's file contains the same structure with `{color.green.N}` values.

### Semantic files reference `{brand.N}`

Light and dark semantic files reference `{brand.N}` rather than `{color.blue.N}`:

```json
{
  "base": {
    "$type": "color",
    "brand": {
      "default": { "$value": "{brand.600}" },
      "hover":   { "$value": "{brand.700}" },
      "active":  { "$value": "{brand.800}" }
    }
  }
}
```

This means the semantic token layer is **brand-agnostic**. The same `light.json` and `dark.json` serve all brands. Switching brand only requires resolving `brand.N` to a different colour ramp — the semantic tokens never need to change.

## Semantic Colour Roles

The semantic layer has a fixed set of colour roles. The role names are constant across all projects and brands. The primitive palette behind each role is configured in `metadata.json` under `roles`.

### Fixed roles

| Role | Purpose | Required |
|---|---|---|
| `brand` | Primary brand/interactive colour | Yes |
| `neutral` | Grey scale, text, borders | Yes |
| `success` | Positive status | Yes |
| `error` | Negative/destructive status | Yes |
| `warning` | Caution status | No |
| `info` | Informational status | No |
| `accent` | Secondary brand colour | No |
| `support` | Tertiary support colour | No |

### Fixed semantic categories

Each role produces the same set of semantic tokens:

```
background.{role}            Page/section background
surface.{role}.default       Component surface
surface.{role}.hover         Surface on hover
surface.{role}.active        Surface on press
border.{role}.default        Component border
base.{role}.default          Solid fill (buttons, badges)
base.{role}.hover            Solid fill on hover
base.{role}.active           Solid fill on press
text.{role}.default          Text on light/tinted surface
text.{role}.contrast         Text on solid (base) surface
icon.{role}.default          Icon on light/tinted surface
icon.{role}.contrast         Icon on solid (base) surface
```

## Composition Overlays

Compositions let you produce additional themed modes by stacking sparse overlay files on top of a base theme. This is defined in `metadata.json`:

```json
{
  "compositions": [
    {
      "name": "Christmas/Light",
      "layers": ["default/light", "occasions/christmas"]
    }
  ]
}
```

`layers` is an ordered array of paths relative to `semantic/` (without `.json`). Later layers override earlier ones with a deep merge. Only the tokens that differ from the base layer need to appear in the overlay file — it is sparse by design.

At build time, each composition produces an additional Figma mode in the Semantic collection.

## Figma Variables Mapping

| Token layer | Figma collection | Modes |
|---|---|---|
| `primitives/` | `Primitives` | `Value` (single mode) |
| `semantic/global/` | `Global` | `Value` (single mode) |
| `semantic/brand/` | `Brand` | One mode per brand: `Default`, `Green`, … |
| `semantic/light.json`, `dark.json`, compositions | `Semantic` | `Light`, `Dark`, + composition modes |

Variable groups in Figma mirror the JSON key hierarchy:
- `surface/brand/hover` ↔ `surface.brand.hover`

Brand collection variables use cross-collection aliases:
- Figma alias `{Primitives/color/blue/600}` ↔ `{color.blue.600}`

Semantic collection variables alias into the Brand collection for brand-coloured tokens:
- Figma alias `{Brand/brand/600}` ↔ `{brand.600}`

This means switching the active brand mode in Figma (or via `[data-brand]` in CSS) cascades through all semantic tokens automatically, without touching the Semantic collection variables.

## Metadata Schema

`metadata.json` is the project configuration file. It is not a token file and does not participate in reference resolution.

```json
{
  "$schema": "tokensync/v1",
  "version": "1.0.0",
  "brands": ["default", "green"],
  "themes": ["light", "dark"],
  "compositions": [
    {
      "name": "Christmas/Light",
      "layers": ["default/light", "occasions/christmas"]
    }
  ],
  "roles": {
    "default": {
      "brand":   "color.blue",
      "neutral": "color.neutral",
      "success": "color.green",
      "error":   "color.red"
    },
    "green": {
      "brand": "color.green"
    }
  },
  "figma": {
    "fileKey": "abc123xyz",
    "collections": {
      "primitives": "Primitives",
      "global":     "Global",
      "brand":      "Brand",
      "semantic":   "Semantic"
    }
  },
  "github": {
    "repo":       "your-org/design-tokens",
    "branch":     "main",
    "tokensPath": "tokens/"
  },
  "platforms": {
    "css":   { "enabled": true, "output": "dist/tokens.css" },
    "js":    { "enabled": true, "output": "dist/{theme}.js", "format": "esm" },
    "ts":    { "enabled": true, "output": "dist/{theme}.ts" },
    "dart":  { "enabled": false, "output": "lib/src/tokens/{theme}.dart" },
    "swift": { "enabled": false, "output": "Sources/Tokens/{theme}.swift" }
  }
}
```

## Platform Output

### CSS

The CSS transformer emits a single file with selector-based brand and theme switching. No separate file per brand is required.

```css
/**
 * Design tokens — generated by Token Sync
 * Do not edit manually.
 */

:root {
  /* primitives */
  --color-blue-600: #1a52d8;
  --color-green-600: #1a8c3a;
  /* ... */

  /* global (theme-invariant) */
  --radius-md: 8px;
  --spacing-inline-4: 16px;
  /* ... */

  /* default brand palette */
  --brand-600: #1a52d8;
  --brand-700: #1240b0;
  /* ... */
}

/* Brand overrides — switch palette by setting [data-brand] on any ancestor */
[data-brand="green"] {
  --brand-600: #1a8c3a;
  --brand-700: #157030;
  /* ... */
}

/* Semantic roles — reference var(--brand-N) so brand switching cascades automatically */
[data-color-scheme="light"] {
  --base-brand-default: var(--brand-600);
  --base-brand-hover:   var(--brand-700);
  --background-default: #ffffff;
  /* ... */
}

[data-color-scheme="dark"] {
  --base-brand-default: var(--brand-400);
  --background-default: #0d0d0d;
  /* ... */
}

[data-color-scheme="auto"] {
  /* same as light — overridden by the media query below */
  --base-brand-default: var(--brand-600);
  /* ... */
}

@media (prefers-color-scheme: dark) {
  [data-color-scheme="auto"] {
    --base-brand-default: var(--brand-400);
    /* ... */
  }
}
```

### JavaScript / TypeScript

```ts
// dist/light.ts
export const tokens = {
  color: {
    base: { brand: { default: "#1a52d8", hover: "#1240b0" } },
    background: { default: "#ffffff" },
    text: { default: "#0d0d0d" }
  },
  radius: { md: "8px" },
  spacing: { inline: { "4": "16px" } }
} as const
```

JS/TS output resolves through the default brand and is not brand-switchable at runtime. It is intended for server-side rendering or environments where CSS custom properties are not available.

### Dart (Flutter)

```dart
// lib/src/tokens/light.dart
class TokensLight {
  static const colorBaseBrandDefault = Color(0xFF1A52D8);
  static const colorBaseBrandHover   = Color(0xFF1240B0);
  static const colorBackgroundDefault = Color(0xFFFFFFFF);
  static const colorTextDefault       = Color(0xFF0D0D0D);
  static const radiusMd               = 8.0;
}
```

## Validation Rules

The build tool enforces these rules:

1. All references must resolve to an existing token
2. No circular references
3. `$type` must be one of the supported types
4. Brand files must only contain `brand.N` tokens
5. `metadata.json` must declare all brands that have files in `semantic/brand/`
6. Required roles (`brand`, `neutral`, `success`, `error`) must be present in all brand role mappings
7. Composition layer paths must reference files that exist in `semantic/`

---

## Versioning

The format version is declared in `metadata.json` under `"version"`. Changes to the format spec increment the minor version. Breaking changes increment the major version.
