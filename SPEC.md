# Token Format Specification — tokensync/v1

## Overview

This document defines the canonical token format used by the Token Sync plugin. It is the source of truth for all token structure decisions.

The format is inspired by the [W3C Design Token Community Group (DTCG)](https://www.w3.org/community/design-tokens/) draft specification, extended with explicit multi-brand and multi-theme support.

---

## File Structure

```
tokens/
  primitives/
    color.json          Raw colour ramps (12 steps per palette)
    geometry.json       Spacing scale, border radius, border width
    typography.json     Font families, sizes, weights, line heights
    motion.json         Durations, easing curves (optional)

  semantic/
    global/             Theme-invariant semantic aliases
      typography.json   Heading, body, label, code composites
      spacing.json      Component spacing, layout spacing, radius aliases
    default/            Default brand — one file per theme
      light.json
      dark.json
    {brand}/            Additional brands — sparse overrides only
      light.json
      dark.json

  metadata.json         Project config: brands, roles, Figma mapping, platform output
```

### Rules

1. **Primitives are raw values only.** No references to other tokens. No semantic meaning.
2. **Global semantics are theme-invariant.** If a token value changes between light and dark, it does not belong in `global/`.
3. **Brand files are sparse.** A brand file only needs to contain tokens that differ from `default/`. Missing tokens resolve from `default/`.
4. **Component code references semantic tokens only.** Never reference primitives directly in UI code.

## Token Syntax

All tokens follow the W3C DTCG format:

```json
{
  "tokenName": {
    "$type": "color",
    "$value": "#0062ba",
    "$description": "Optional human-readable description"
  }
}
```

`$type` can be set on a group and inherited by all children:

```json
{
  "surface": {
    "$type": "color",
    "default":  { "$value": "#ffffff" },
    "disabled": { "$value": "#f0f0f0" }
  }
}
```

### Supported types

| Type | Example value | Used in |
|---|---|---|
| `color` | `"#0062ba"`, `"rgba(0,0,0,0.1)"` | All colour tokens |
| `dimension` | `"16px"`, `"1rem"` | Spacing, radius, font-size |
| `fontFamily` | `"Inter, sans-serif"` | Typography |
| `fontWeight` | `"600"` | Typography |
| `number` | `"1.5"` | Line height, opacity |
| `shadow` | `"0 2px 4px {color.black.10}"` | Elevation |

## Reference Syntax

References use W3C DTCG curly-brace syntax:

```
{token.path.here}
```

All token files are merged into one flat namespace at resolution time. The path follows the JSON key hierarchy, ignoring the file or folder location.

### Examples

```json
"$value": "{color.brand.600}"
```
→ resolves via `primitives/color.json` → `color` → `brand` → `600`

```json
"$value": "{text.brand.default}"
```
→ resolves via `semantic/default/light.json` → `text` → `brand` → `default`

```json
"$value": "{geometry.size.4}"
```
→ resolves via `primitives/geometry.json` → `geometry` → `size` → `4` → `"16px"`

### Circular references

Circular references are not permitted and will fail validation. The tool reports the full reference chain on error.

## Colour Primitive Model

Colour ramps use a 12-step scale. Steps are named by perceptual lightness position, not arbitrary numbers:

| Step | Perceptual role |
|---|---|
| `25`  | Lightest background tint |
| `50`  | Light background tint |
| `100` | Surface tint |
| `200` | Subtle border, surface active |
| `300` | Border, surface hover |
| `400` | Muted interactive |
| `500` | Mid-point (equal perceived darkness across all palettes) |
| `600` | Primary interactive default |
| `700` | Primary interactive hover |
| `800` | Primary interactive active |
| `900` | Deep background (dark mode) |
| `950` | Deepest background (dark mode) |

**Key property:** `green.500` and `blue.500` have the same perceived darkness. This is guaranteed by the OKLCH generation in Themebuilder. It makes the system predictable: you can reason about contrast ratios by step number alone.

Ramps are generated by Themebuilder from a single seed colour using OKLCH colour space with fixed per-step luminance targets. The source of truth is always the seed — ramps are never manually edited.

## Semantic Colour Roles

The semantic layer has a fixed set of colour roles. The role names are constant across all projects and brands. The primitive palette behind each role is configured in `metadata.json` under `roles`.

### Fixed roles

| Role | Purpose | Required |
|---|---|---|
| `brand` | Primary brand/interactive colour | Yes |
| `neutral` | Grey scale, text, borders | Yes |
| `success` | Positive status | Yes |
| `error` | Negative/destructive status | Yes |
| `warning` | Caution status | No |
| `info` | Informational status | No |
| `accent` | Secondary brand colour | No |
| `support` | Tertiary support colour | No |

### Fixed semantic categories

Each role produces the same set of semantic tokens:

```
background.{role}            Page/section background
surface.{role}.default       Component surface
surface.{role}.hover         Surface on hover
surface.{role}.active        Surface on press
border.{role}.default        Component border
base.{role}.default          Solid fill (buttons, badges)
base.{role}.hover            Solid fill on hover
base.{role}.active           Solid fill on press
text.{role}.default          Text on light/tinted surface
text.{role}.contrast         Text on solid (base) surface
icon.{role}.default          Icon on light/tinted surface
icon.{role}.contrast         Icon on solid (base) surface
```

## Multi-Brand Inheritance

Brand files are overlays. Resolution order for a given brand/theme combination:

```
1. primitives/color.json
2. primitives/geometry.json
3. primitives/typography.json
4. semantic/global/typography.json
5. semantic/global/spacing.json
6. semantic/default/{theme}.json   ← base
7. semantic/{brand}/{theme}.json   ← overrides (if brand ≠ default)
```

A brand file only needs to specify what it overrides. Example: if `brand-a` uses the same success colour as `default` but a different brand colour, `brand-a/light.json` only contains:

```json
{
  "base": {
    "brand": {
      "default": { "$value": "{color.forest.600}" },
      "hover":   { "$value": "{color.forest.700}" },
      "active":  { "$value": "{color.forest.800}" }
    }
  }
}
```

## Figma Variables Mapping

| Token layer | Figma collection | Modes |
|---|---|---|
| `primitives/` | `Primitives` | `Value` (single mode) |
| `semantic/global/` | `Global` | `Value` (single mode) |
| `semantic/{brand}/{theme}` | `Semantic` | `Default/Light`, `Default/Dark`, `Brand-A/Light`, … |

Variable groups in Figma mirror the JSON key hierarchy:
- `surface/brand/hover` ↔ `surface.brand.hover`

Variable aliases in Figma (references) map 1:1 to token references:
- Figma alias `{Semantic/Default/Light/text/brand/default}` ↔ `{text.brand.default}`

## Metadata Schema

`metadata.json` is the project configuration file. It is not a token file and does not participate in reference resolution.

```json
{
  "$schema": "tokensync/v1",
  "version": "1.0.0",
  "brands": ["default", "brand-a"],
  "themes": ["light", "dark"],
  "roles": {
    "default": {
      "brand":   "color.brand",
      "neutral": "color.neutral",
      "success": "color.success",
      "error":   "color.error"
    },
    "brand-a": {
      "brand": "color.forest"
    }
  },
  "figma": {
    "fileKey": "abc123xyz",
    "collections": {
      "primitives": "Primitives",
      "global":     "Global",
      "semantic":   "Semantic"
    }
  },
  "github": {
    "repo":       "your-org/design-tokens",
    "branch":     "main",
    "tokensPath": "tokens/"
  },
  "platforms": {
    "css":   { "enabled": true, "output": "dist/{brand}/{theme}.css", "prefix": "--" },
    "js":    { "enabled": true, "output": "dist/{brand}/{theme}.js", "format": "esm" },
    "ts":    { "enabled": true, "output": "dist/{brand}/{theme}.ts" },
    "dart":  { "enabled": false, "output": "lib/src/tokens/{brand}_{theme}.dart" },
    "swift": { "enabled": false, "output": "Sources/Tokens/{brand}/{theme}.swift" }
  }
}
```

## Platform Output

The build tool transforms the resolved token tree into platform-specific files. All references are fully resolved — no CSS `var()` chains for colour tokens, no runtime math.

### CSS

```css
/* dist/default/light.css */
:root, [data-color-scheme="light"] {
  --color-background-default: #ffffff;
  --color-surface-brand-default: #e0ecff;
  --color-base-brand-default: #1a52d8;
  --color-text-default: #0d0d0d;
  --radius-md: 8px;
  --spacing-inline-4: 16px;
}

@media (prefers-color-scheme: dark) {
  :root:not([data-color-scheme="light"]) {
    --color-background-default: #0d0d0d;
    /* ... */
  }
}

[data-color-scheme="dark"] {
  --color-background-default: #0d0d0d;
  /* ... */
}
```

### JavaScript / TypeScript

```ts
// dist/default/light.ts
export const tokens = {
  color: {
    background: { default: "#ffffff" },
    base: { brand: { default: "#1a52d8", hover: "#1240b0" } },
    text: { default: "#0d0d0d" }
  },
  radius: { md: "8px" },
  spacing: { inline: { "4": "16px" } }
} as const
```

### Dart (Flutter)

```dart
// lib/src/tokens/default_light.dart
class TokensDefaultLight {
  static const colorBackgroundDefault = Color(0xFFFFFFFF);
  static const colorBaseBrandDefault  = Color(0xFF1A52D8);
  static const colorTextDefault       = Color(0xFF0D0D0D);
  static const radiusMd               = 8.0;
}
```

## Validation Rules

The build tool enforces these rules at build time and as part of the GitHub PR check:

1. All references must resolve to an existing token
2. No circular references
3. `$type` must be valid (see supported types above)
4. Brand files may only contain tokens that exist in `semantic/default/{theme}`
5. `metadata.json` must declare all brands that have files in `semantic/`
6. Required roles (`brand`, `neutral`, `success`, `error`) must be present in all brands

---

## Versioning

The format version is declared in `metadata.json` under `"version"`. Changes to the format spec increment the minor version. Breaking changes increment the major version. The build tool validates compatibility on load.
