# Token Format Specification — tokensync/v1

## Overview

This document defines the canonical token format used by the Token Sync plugin. It is the source of truth for all token structure decisions.

The format is inspired by the [W3C Design Token Community Group (DTCG)](https://www.w3.org/community/design-tokens/) draft specification, extended with explicit multi-theme and multi-color-scheme support.

---

## File Structure

```
tokens/
  primitives/
    color.json          Raw colour ramps (12 steps per palette)
    geometry.json       Spacing scale, border radius, border width
    typography.json     Font families, sizes, weights, line heights
    motion.json         Durations, easing curves (optional)

  semantic/
    global/             Theme-invariant semantic aliases
      typography.json   Heading, body, label, code composites
      spacing.json      Component spacing, layout spacing, radius aliases
    themes/             Complete light + dark token sets — one file per named theme
      original.json     "Original" theme: light.* and dark.* token trees
      {name}.json       Additional themes (Zero, Vanilla, …)
    light.json          Semantic colour roles — light color scheme
    dark.json           Semantic colour roles — dark color scheme

  metadata.json         Project config: themes, colorSchemes, Figma mapping, platform output
```

### Rules

1. **Primitives are raw values only.** No references to other tokens. No semantic meaning.
2. **Global semantics are color-scheme-invariant.** If a token value changes between light and dark, it does not belong in `global/`.
3. **Theme files contain the complete light and dark semantic token set** for brand/neutral tokens. Each theme file has a `light` section and a `dark` section, each containing the full set of non-severity tokens.
4. **Semantic files (`light.json`, `dark.json`) reference `{light.*}` and `{dark.*}`** for brand/neutral tokens. This is a cross-collection alias — the active theme's mode determines which values are resolved. Severity tokens (success/error/warning/info) reference primitives directly.
5. **Component code references semantic tokens only.** Never reference primitives or theme tokens directly in UI code.

## Token Syntax

All tokens follow the W3C DTCG format:

```json
{
  "tokenName": {
    "$type": "color",
    "$value": "#0062ba",
    "$description": "Optional human-readable description"
  }
}
```

`$type` can be set on a group and inherited by all children:

```json
{
  "surface": {
    "$type": "color",
    "default":  { "$value": "#ffffff" },
    "disabled": { "$value": "#f0f0f0" }
  }
}
```

### Supported types

| Type | Example value | Used in |
|---|---|---|
| `color` | `"#0062ba"`, `"rgba(0,0,0,0.1)"` | All colour tokens |
| `dimension` | `"16px"`, `"1rem"` | Spacing, radius, font-size |
| `fontFamily` | `"Inter, sans-serif"` | Typography |
| `fontWeight` | `"600"` | Typography |
| `number` | `"1.5"` | Line height, opacity |
| `shadow` | `"0 2px 4px {color.black.10}"` | Elevation |

## Reference Syntax

References use W3C DTCG curly-brace syntax:

```
{token.path.here}
```

All token files are merged into one flat namespace at resolution time. The path follows the JSON key hierarchy, ignoring file or folder location.

### Examples

```json
"$value": "{color.blue.600}"
```
→ resolves via `primitives/color.json` → `color` → `blue` → `600`

```json
"$value": "{light.base.brand.default}"
```
→ resolves via `semantic/themes/original.json` (active theme) → `light` → `base` → `brand` → `default`

```json
"$value": "{geometry.size.4}"
```
→ resolves via `primitives/geometry.json` → `geometry` → `size` → `4` → `"16px"`

### Circular references

Circular references are not permitted and will fail validation.

## Colour Primitive Model

Colour ramps use a 12-step scale. Steps are named by perceptual lightness position:

| Step | Perceptual role |
|---|---|
| `25`  | Lightest background tint |
| `50`  | Light background tint |
| `100` | Surface tint |
| `200` | Subtle border, surface active |
| `300` | Border, surface hover |
| `400` | Muted interactive |
| `500` | Mid-point (equal perceived darkness across all palettes) |
| `600` | Primary interactive default |
| `700` | Primary interactive hover |
| `800` | Primary interactive active |
| `900` | Deep background (dark mode) |
| `950` | Deepest background (dark mode) |

**Key property:** `green.500` and `blue.500` have the same perceived darkness. This is guaranteed by the OKLCH generation in Themebuilder. It makes the system predictable: you can reason about contrast ratios by step number alone.

Ramps are generated by Themebuilder from a single seed colour using OKLCH colour space with fixed per-step luminance targets. The source of truth is always the seed — ramps are never manually edited.

## Theme Model

The Themes collection introduces a named theme layer between semantic tokens and colour primitives. Each theme defines the complete set of brand and neutral colour roles for both light and dark color schemes.

### Theme files (`semantic/themes/{name}.json`)

Each theme file contains a `light` section and a `dark` section. Both sections contain the full set of non-severity semantic tokens, referencing primitives directly:

```json
{
  "light": {
    "background": {
      "$type": "color",
      "default": { "$value": "{color.white.950}" },
      "brand":   { "$value": "{color.blue.25}" }
    },
    "base": {
      "$type": "color",
      "brand": {
        "default": { "$value": "{color.blue.600}" },
        "hover":   { "$value": "{color.blue.700}" },
        "active":  { "$value": "{color.blue.800}" }
      }
    }
  },
  "dark": {
    "background": {
      "$type": "color",
      "default": { "$value": "{color.neutral.950}" },
      "brand":   { "$value": "{color.blue.950}" }
    },
    "base": {
      "$type": "color",
      "brand": {
        "default": { "$value": "{color.blue.500}" },
        "hover":   { "$value": "{color.blue.400}" },
        "active":  { "$value": "{color.blue.300}" }
      }
    }
  }
}
```

A second theme (e.g. `zero.json`) uses the same structure but maps to different primitive steps — for example, tighter neutral steps or a different brand hue.

### Semantic files reference `{light.*}` and `{dark.*}`

`light.json` and `dark.json` reference theme tokens via cross-collection aliases:

```json
{
  "base": {
    "$type": "color",
    "brand": {
      "default": { "$value": "{light.base.brand.default}" },
      "hover":   { "$value": "{light.base.brand.hover}" },
      "active":  { "$value": "{light.base.brand.active}" }
    }
  }
}
```

This means the semantic files are **theme-agnostic** for brand/neutral tokens. The active theme determines which primitive values are resolved. Severity tokens (success/error/warning/info) reference primitives directly because they are identical across all themes.

## Semantic Colour Roles

The semantic layer has a fixed set of colour roles. The role names are constant across all projects and themes.

### Fixed roles

| Role | Purpose | Source |
|---|---|---|
| `brand` | Primary brand/interactive colour | Defined per theme |
| `neutral` | Grey scale, text, borders | Defined per theme |
| `success` | Positive status | Direct primitive ref (`{color.green.N}`) |
| `error` | Negative/destructive status | Direct primitive ref (`{color.red.N}`) |
| `warning` | Caution status | Direct primitive ref (`{color.amber.N}`) |
| `info` | Informational status | Direct primitive ref (`{color.sky.N}`) |

### Fixed semantic categories

Each role produces the same set of semantic tokens:

```
background.{role}            Page/section background
surface.{role}.default       Component surface
surface.{role}.hover         Surface on hover
surface.{role}.active        Surface on press
border.{role}.default        Component border
base.{role}.default          Solid fill (buttons, badges)
base.{role}.hover            Solid fill on hover
base.{role}.active           Solid fill on press
text.{role}.default          Text on light/tinted surface
text.{role}.contrast         Text on solid (base) surface
icon.{role}.default          Icon on light/tinted surface
icon.{role}.contrast         Icon on solid (base) surface
```

## Figma Variables Mapping

| Token layer | Figma collection | Modes |
|---|---|---|
| `primitives/` | `Primitives` | `Value` (single mode) |
| `semantic/global/` | `Global` | `Value` (single mode) |
| `semantic/themes/` | `Themes` | One mode per named theme: `Original`, `Christmas`, … |
| `semantic/light.json`, `dark.json` | `Semantic` | `Light`, `Dark`, + any additional viewing modes |

Variable groups in Figma mirror the JSON key hierarchy:
- `surface/brand/hover` ↔ `surface.brand.hover`

Themes collection variables use cross-collection aliases into Primitives:
- Figma alias `{Primitives/color/blue/600}` ↔ `{color.blue.600}`

Semantic collection variables alias into the Themes collection for brand/neutral tokens:
- Figma alias `{Themes/light/base/brand/default}` ↔ `{light.base.brand.default}`

Switching the active theme mode in Figma (or via `[data-theme]` in CSS) cascades through all brand and neutral semantic tokens automatically, without touching the Semantic collection variables.

## Metadata Schema

`metadata.json` is the project configuration file. It is not a token file and does not participate in reference resolution.

```json
{
  "$schema": "tokensync/v1",
  "version": "1.0.0",
  "themes": ["original", "christmas"],
  "colorSchemes": ["light", "dark"],
  "figma": {
    "fileKey": "abc123xyz",
    "collections": {
      "primitives": "Primitives",
      "global":     "Global",
      "themes":     "Themes",
      "semantic":   "Semantic"
    }
  },
  "github": {
    "repo":       "your-org/design-tokens",
    "branch":     "main",
    "tokensPath": "tokens/"
  },
  "platforms": {
    "css":   { "enabled": true, "output": "dist/tokens.css" },
    "js":    { "enabled": true, "output": "dist/{colorScheme}.js", "format": "esm" },
    "ts":    { "enabled": true, "output": "dist/{colorScheme}.ts" },
    "dart":  { "enabled": false, "output": "lib/src/tokens/{colorScheme}.dart" },
    "swift": { "enabled": false, "output": "Sources/Tokens/{colorScheme}.swift" }
  }
}
```

## Platform Output

### CSS

The CSS transformer emits a single file with attribute-based theme and color-scheme switching.

```css
/**
 * Design tokens — generated by Token Sync
 * Do not edit manually.
 */

:root {
  /* primitives */
  --color-blue-600: #1a52d8;
  --color-green-600: #1a8c3a;
  /* ... */

  /* global (color-scheme-invariant) */
  --radius-md: 8px;
  --spacing-inline-4: 16px;
  /* ... */

  /* default theme — light and dark vars available to Semantic selectors */
  --light-background-default: #ffffff;
  --light-base-brand-default: #1a52d8;
  --dark-background-default: #111111;
  --dark-base-brand-default: #5b8af5;
  /* ... */
}

/* Non-default theme overrides — set [data-theme] on any ancestor to switch */
[data-theme="zero"] {
  --light-background-default: #f8f8f8;
  --light-base-brand-default: #0e47d4;
  --dark-background-default: #0d0d0d;
  --dark-base-brand-default: #6a96f7;
  /* ... */
}

/* Semantic roles — reference var(--light-*) / var(--dark-*) for theme cascade */
[data-color-scheme="light"] {
  --base-brand-default: var(--light-base-brand-default);
  --background-default: var(--light-background-default);
  --background-success: #f0fdf4;  /* severity — direct primitive, theme-independent */
  /* ... */
}

[data-color-scheme="dark"] {
  --base-brand-default: var(--dark-base-brand-default);
  --background-default: var(--dark-background-default);
  --background-success: #052e16;
  /* ... */
}

[data-color-scheme="auto"] {
  /* defaults to light */
  --base-brand-default: var(--light-base-brand-default);
  /* ... */
}

@media (prefers-color-scheme: dark) {
  [data-color-scheme="auto"] {
    --base-brand-default: var(--dark-base-brand-default);
    /* ... */
  }
}
```

### JavaScript / TypeScript

```ts
// dist/light.ts
export const tokens = {
  color: {
    base: { brand: { default: "#1a52d8", hover: "#1240b0" } },
    background: { default: "#ffffff" },
    text: { default: "#0d0d0d" }
  },
  radius: { md: "8px" },
  spacing: { inline: { "4": "16px" } }
} as const
```

JS/TS output resolves through the default theme and is not theme-switchable at runtime. It is intended for server-side rendering or environments where CSS custom properties are not available.

### Dart (Flutter)

```dart
// lib/src/tokens/light.dart
class TokensLight {
  static const colorBaseBrandDefault = Color(0xFF1A52D8);
  static const colorBaseBrandHover   = Color(0xFF1240B0);
  static const colorBackgroundDefault = Color(0xFFFFFFFF);
  static const colorTextDefault       = Color(0xFF0D0D0D);
  static const radiusMd               = 8.0;
}
```

## Validation Rules

The build tool enforces these rules:

1. All references must resolve to an existing token
2. No circular references
3. `$type` must be one of the supported types
4. Theme files must contain both a `light` and a `dark` section
5. `metadata.json` must declare all themes that have files in `semantic/themes/`
6. Severity roles (`success`, `error`, `warning`, `info`) in semantic files must reference primitives directly, not `{light.*}` or `{dark.*}` aliases

---

## Versioning

The format version is declared in `metadata.json` under `"version"`. Changes to the format spec increment the minor version. Breaking changes increment the major version.
